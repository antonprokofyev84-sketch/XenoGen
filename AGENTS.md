## Код и ответственность

Стек: React 19, TypeScript strict, Zustand + Immer, SCSS, Vite; пакеты — npm.

| Каталог / файл                          | Назначение                                                |
| --------------------------------------- | --------------------------------------------------------- |
| `src/features/`, `src/components/`      | Экраны, локальные и общие UI-компоненты                   |
| `src/systems/`                          | Игровые правила и исполнение команд                       |
| `src/state/gameSlices/`                 | Состояние и публичные команды; сборка в `useGameState.ts` |
| `src/types/`                            | Общие доменные типы, плоская структура                    |
| `src/data/initial/`                     | Immutable-реестры; `bundle.ts` собирает их для validator  |
| `src/data/initial/fixtures/`            | Технический контент для проверки контрактов               |
| `src/systems/world/newGameBootstrap.ts` | Сборка мира новой игры                                    |

`App.tsx` выбирает экран через `ui.currentScreen`. Сохраняй существующие имена slices
и используй их команды. `useCombatState` и `useMapInteractionStore` — отдельные stores.

- Разделяй definitions, изменяемый runtime и производное представление.
- Связанные изменения мира, времени и interaction выполняй одной Immer-транзакцией
  через draft helpers. Внутри helper не вызывай вложенные `set` других slices.
- React отображает готовые данные и отправляет команды. Броски, расходы и effects
  выполняются в systems. Объектные и массивные Zustand-селекторы мемоизируй.
- Игровую случайность проводи через `Rng` из `src/systems/rolls/rng.ts`;
  воспроизводимые сценарии — через `createSeededRng`.
- `ActionNumber` — чистая функция переданного `ActionContext`.
- Новые абстракции и effects вводи под конкретный игровой сценарий.

## Простота и предусловия

- Код должен быть максимально простым и читаемым, с минимумом guards.
  Исполнитель делает указанное действие и опирается на предусловия,
  установленные вызывающим кодом.
- Перед добавлением guard проследи реальные вызовы и назови достижимый сценарий,
  в котором условие нарушается. Nullable-тип, публичность метода, гипотетический
  будущий вызов или искусственный вызов из теста сами по себе не обосновывают guard.
  Проверка невозможного состояния вводит читателя в заблуждение: она создаёт
  впечатление, что такой исход предусмотрен игровым флоу.
- Гарантированные данные можно получать из state без повторной проверки наличия.
  Например, вызов Action из текущего interaction не требует `if (!interaction)`.
  Если функция уже получает state, не передавай дополнительно извлечённый из него
  interaction или POI только ради обхода nullable-типа.
- Не добавляй runtime-ветвления ради TypeScript. Уточняй тип под предусловия
  конкретной операции; при доказанной гарантии допустим локальный non-null assertion.
  Каждый non-null assertion (`!`) сопровождай комментарием: какой вызов, проверка
  или инвариант гарантирует наличие значения именно в этом месте.
  Nullable-поле в общем store не означает, что отсутствие объекта возможно
  при каждом его использовании.
- Передача ID вглубь синхронной цепочки не требует повторной проверки объекта.
  Учитывай конкретные вызовы, способные изменить его существование: именно они,
  а не глубина вызова, могут потребовать новой проверки.
- Различай нарушение инварианта и нормальный игровой исход. Уход NPC после
  изменения времени — игровое условие; исчезновение гарантированного контекста
  внутри синхронной операции — ошибка. Нарушение инварианта должно быть заметно:
  не скрывай его через ранний return, `console.warn` с продолжением или подстановку
  пустого/нулевого результата. Предпочитай явную ошибку в месте нарушения.
- Не заменяй каждый guard на assert/throw: убирай повторные проверки гарантированных
  фактов. Проверяй внешние данные на входе, игровые условия — в управляющем сценарии
  в момент, когда они действительно могут измениться. Нормальное отсутствие данных
  в query или необязательное поле обрабатывай согласно их контракту.

## Стиль

- Импорты из `src` — через `@/`; типы — через type-only imports.
- Вложенные тернарные операторы запрещены правилом `no-nested-ternary`.
  Выбор по discriminator оформляй через `switch`, остальные ветвления — `if/else`.
- Форматирование задаёт `.prettierrc`: 2 пробела, single quotes, semicolons,
  trailing commas, ширина 100. Форматируй затронутые файлы.
- UI-тексты и параметры переводов — доменные файлы в `src/locales/en/`, собранные
  через `src/locales/en.ts`, и `t` из
  `src/systems/text/i18n.ts`. Художественный текст — inline `LocalizedText`
  через `resolveText()` и существующие narrative helpers.
- Для UI используй общие `GameScene`, `GameHud`, `GameSystemMenu`, `GameTooltip`
  и `game-button`; оформление задано в [POI UI](docs/new/poi-ui-design.md).
- При работе с изображениями следуй [стандарту ассетов](docs/new/visual-assets.md).
  SCSS-переменные инжектируются Vite.

## Проверка и сдача

- В начале задачи проверь Git status, сохрани изменения пользователя.
- Для кода основной gate — `npm run build`; запускай подходящие тесты и ESLint
  затронутых TS/TSX. Общий ESLint содержит существующий долг — отделяй его от новых ошибок.
- Контент проверяй через `validateInitialData` / `assertValidInitialData`:
  dev entry point только пишет ошибки в консоль. Исправляй данные явно.
- Runtime проверяй на fixtures: вход/выход, success/fail, лимиты, смена time slot/дня,
  force exit, удаление POI, квестовый переход и открытие торговли — по области изменения.
- Для документации проверяй ссылки, пути и `git diff --check`.
- В отчёте укажи результат, проверки и оставшиеся расхождения.
  Коммиты, push и публикацию выполняй по явному запросу.
