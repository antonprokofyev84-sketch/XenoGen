# Interaction Runtime: статус решений

Этот документ больше не является повторным списком вопросов. Он отделяет уже принятый runtime-контракт от действительно отложенных решений. Подробности находятся в профильных документах.

## Принято

### Interaction state и root-контент

- Текущий контекст — POI либо slot/NPC с обязательной парой `slotId + npcId`.
- `pendingEvents` — одна очередь автоматических interaction events, упорядоченная по priority. Authored Interceptors представлены элементами с `interceptorId`; system `forceExit` — отдельным вариантом union, а не записью `INITIAL_INTERCEPTORS`.
- Root-варианты собираются группами по источнику: `frame`, `poi`, `slot`, `personal`, `quest`; навигационные переходы к slots и POI строятся из состояния мира отдельно.
- После любого завершённого Action заново собираются все варианты окончательного видимого экрана. Повторного полного resolver/recheck выбранного Action в начале `performAction` нет.

### Исполнение Action

1. Один раз разрешить cost, авансом списать деньги, предметы и stamina протагониста, сохранить `cost.time` до завершающего мирового действия и учесть начатую попытку в execution limit.
2. Выполнить check и выбрать result.
3. Последовательно применить effects и записать resolved narrative в log исходного контекста.
4. Выполнить transition. Перемещение делегируется стандартному мировому действию `moveToPoi`, которому передаётся отложенный `cost.time` вместе с обычными затратами пути без двойного списания. Если перемещения нет, отложенное время передаётся `spendTime`, `rest` или другому подходящему мировому действию.
5. Завершить последствия мирового действия, дождаться root для pending events и заново собрать все варианты экрана, который фактически будет показан.

Переход в другой POI из authored Action допустим, но обычные перемещения предпочтительно показывать явной навигацией мира: так стандартные затраты пути применяются автоматически.

### Interceptors и forceExit

- Authored Interceptors собираются в одну очередь по priority. Перед исполнением извлечённого Interceptor его conditions проверяются повторно.
- Interceptor без Frame продолжается сразу; Interceptor с Frame приостанавливает очередь до возврата в root.
- Смена time slot заменяет оставшуюся authored-часть очереди актуальным снимком.
- `forceExit` планируется как идемпотентный system item, заменяет authored-остаток, переживает refresh time slot и исполняется только после возвращения в root текущего контекста. Внутренний Frame он не прерывает.
- Reserved force-exit Frame может описать авторский исход. Без него применяется системный fallback: slot/NPC → текущий POI, POI → родительский POI.

### Контекст, log и background

- Переход в другой Frame того же контекста сохраняет log.
- Переход POI ↔ slot/NPC или между POI начинает новый log.
- Log хранит только один раз разрешённые narrative blocks; presentation snapshot не сохраняется.
- Переход POI ↔ slot/NPC не сбрасывает background. Новый root Frame заменяет его, только если задаёт собственный `background`; иначе действует обычное наследование.
- Переход в другой POI через мировое перемещение либо полное завершение interaction сбрасывает background перед первым Frame нового interaction.

### Время, occupancy и конец дня

- Фактическая slot occupancy создаётся лениво при первом входе в POI в текущем time slot и затем кешируется.
- Resolved schedule NPC является глобальным. `baseSchedule: 'work'` задаёт время работы, а candidate/assignment work slot — возможное рабочее место. При совпадении и открытом POI тот резервирует NPC даже до посещения: NPC не может появиться во `freeTime`/`home`. Конкретный occupant и chance разрешаются только при входе; без успешного рабочего размещения fallback в другие группы нет.
- Один общий `onDayEnd` обрабатывает все зарегистрированные мировые счётчики оставшихся дней, POI day effects, квестовые таймеры и собранные effects, removal sweep и очистку дневной interaction memory в зафиксированном порядке.
- `entryDisabledDaysLeft` участвует в общей фазе дневных счётчиков наравне с остальными; отдельного pipeline для него нет.

### Tension

- Дневной `tension` принадлежит NPC и рассчитывается один раз при первом взаимодействии с ним за день.
- База берётся из текущей реализации: weighted effective relation и целое случайное отклонение `[-20, 20]`. Исправленная формула: `clamp(-effectiveRelation + randomOffset, 0, 100)`.
- В конце дня дневная запись удаляется. Конкретный порог `forceExit` остаётся балансной константой.

## Действительно остаётся открытым

1. Боевой transition и возврат из combat.
2. Числовое значение порога `forceExit` и возможные дополнительные trigger types помимо проверки после initialization/restoration и полного результата с `modifyTension`.
3. Расширенный visual-variant resolver персонажей. Базовый layout уже принят.
4. Save/load и восстановление runtime state — вне текущей миграции.
5. Новые effects вне утверждённого первого каталога добавляются только под конкретный сценарий.
