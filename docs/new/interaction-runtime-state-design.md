# Interaction runtime: состояние, варианты UI и исполнение Action

## Статус и границы

Этот документ фиксирует решения по **пунктам 1–3** из `interaction-runtime-open-questions.md`: структуру interaction state, сборку вариантов для UI и исполнение Action. Формы TypeScript — проектируемый контракт, а не описание уже написанного кода.

Очередь Interceptors, общий порядок дневных систем и детали внешних режимов рассматриваются в следующих пунктах runtime-дизайна. Здесь зафиксированы только их уже согласованные связи с Action.

## 1. Текущий контекст

В текущем interaction всегда есть ID **конкретного экземпляра** POI. Если игрок взаимодействует с NPC в slot этого POI, вместе присутствуют `slotId` и `npcId`. Если обоих полей нет, это контекст самого POI. Отдельный `type` и вложенный объект `context` не нужны.

```ts
type CurrentInteraction = (
  | {
      poiId: PoiId;
      slotId?: never;
      npcId?: never;
    }
  | {
      poiId: PoiId;
      slotId: SlotId;
      npcId: NpcId;
    }
) & {
  activeFrameId: FrameId;
  pendingEvents: PendingInteractionEvent[];
  currentBackground?: ResolvedBackground;
  log: InteractionLogEvent[];
};

type PendingInteractionEvent =
  | { type: 'interceptor'; interceptorId: InterceptorId }
  | { type: 'forceExit' };
```

`ResolvedBackground` и `InteractionLogEvent` здесь обозначают runtime-данные представления. Если Frame не задаёт background, показывается уже выбранный фон. Travel в другой POI или полное завершение interaction сбрасывает фон перед первым Frame нового interaction. Переключение POI root ↔ slot/NPC context не сбрасывает фон: slot root без собственного background может наследовать фон POI. Narrative, уже показанный игроку, хранится в `log` как разрешённые blocks, чтобы не вычислять его повторно.

Union запрещает при типизированной записи сочетания `poiId + slotId` без `npcId` и `poiId + npcId` без `slotId`. При смене контекста следует заменять `CurrentInteraction` целиком, не мутируя отдельные идентификаторы в разных store-операциях. TypeScript проверяет места записи в исходном коде, а runtime дополнительно проверяет внешние входные данные и то, что NPC действительно занимает указанный slot. Save/load здесь не предполагается.

Контекст нельзя восстанавливать из строки `activeFrameId`: квестовый Frame может называться по NPC или квесту, а конкретный `poiId` задаётся отдельно. `slotId` определяет место/роль, `npcId` — фактического occupant.

## 2. Активный Frame и повторный вход

`activeFrameId` всегда содержит настоящий ID Frame. `undefined` не означает root. POI root имеет ID своего `templateId` (например, `redBoar`); slot root — `templateId/slotId` (например, `redBoar/bartender`). Это IDs definitions, а не ID конкретного экземпляра POI или NPC.

При новом входе собирается очередь Interceptors. Событие может открыть внутренний Frame; если очередь не открыла Frame, показывается root. Вход обрабатывается как одна runtime-операция, поэтому UI не должен сначала мельком показать root перед событием. Дополнительный `isEntering`/`interactionPhase` для этого не требуется.

Выход из разговора или POI завершает текущий вход. Повторный подход создаёт новый контекст и начинает заново с pending events/root; оставленный внутренний Frame **не восстанавливается**. Это принятое правило поведения, а не техническое ограничение. Поведение загрузки save внутри Frame здесь не задаётся: save/load находится вне текущей миграции.

## 3. Очередь Interceptors

`pendingEvents` — единственная очередь только текущего контекста, а не карта очередей всех посещённых контекстов. Обычный элемент ссылается на authored Interceptor; system `forceExit` является отдельным вариантом union и не маскируется под `InterceptorId`. Interceptors не являются кнопками UI.

- При новом входе сначала восстанавливается или рассчитывается дневное состояние субъекта, затем собирается актуальная очередь authored Interceptors. Если восстановленный tension NPC уже достиг порога, `scheduleForceExit` заменяет authored items до начала исполнения очереди. Каждый оставшийся authored item извлекается из массива до исполнения и повторной проверки условий.
- Silent Interceptor продолжает очередь; открытие внутреннего Frame приостанавливает остаток до возврата в root **того же** контекста.
- Смена контекста, выход или внешний переход удаляют старую очередь; очередь родителя при возвращении не возобновляется.
- После атомарного изменения времени со сменой time slot сначала обновляются schedules и occupancy и проверяется существование текущего контекста, затем authored-очередь заменяется новой для конечного time slot. Промежуточные time slots не запускают события. Уже запланированный system `forceExit` переживает такую актуализацию и продолжает заменять authored-очередь до исполнения либо выхода из контекста.
- Если игрок остался во внутреннем Frame, новая очередь ждёт root. Перед её первым запуском в slot/NPC-контексте после очистки daily memory runtime вызывает `ensureNpcDailyTension()`. Если occupant ушёл из slot, прежний NPC-контекст закрывается и для него очередь не строится.
- При достижении утверждённого trigger `scheduleForceExit` идемпотентно очищает authored items и оставляет единственный `{ type: 'forceExit' }` только в slot/NPC-контексте. Он не прерывает внутренний Frame и исполняется только в root. Выход из контекста, удаление POI или инвалидированный slot/NPC context очищает его.

Дополнительный `handledInterceptorIds` не нужен. Повторяемость authored Interceptors при новых входах и пересборках определяется актуальными условиями, `executionLimit` и дневной памятью. Полный порядок исполнения зафиксирован в `interceptors-design.md`; system `forceExit` использует ту же очередь, но не проходит authoring checks.

## 4. Subject и два срока жизни памяти

Ключ памяти исполнения — `subject + executableId`. Для POI-контекста subject — конкретный `poiId`, для slot/NPC-контекста — конкретный `npcId`. `slotId` и `frameId` в ключ не входят. Actions и Interceptors разделены, потому что их IDs относятся к разным реестрам.

```ts
type InteractionSubjectKey = `poi:${PoiId}` | `npc:${NpcId}`;

interface DailyExecutableMemory {
  executions?: number; // только при executionLimit.perDay
  appeared?: boolean; // только при appearanceChance
}

interface SubjectDailyInteractionMemory {
  actions: Partial<Record<ActionId, DailyExecutableMemory>>;
  interceptors: Partial<Record<InterceptorId, DailyExecutableMemory>>;
  /**
   * Дневной tension; только для npc-subject.
   * Резолвится при первом взаимодействии за деньб переиспользуется при повторных,
   * стирается в конце дня. См tension-force-exit-and-poi-entry.md
   */
  tension?: number;
  // Другие дневные данные subject, если они ему нужны.
}

type DailyInteractionMemoryBySubject = Partial<
  Record<InteractionSubjectKey, SubjectDailyInteractionMemory>
>;

interface SubjectExecutionTotals {
  actions: Partial<Record<ActionId, number>>;
  interceptors: Partial<Record<InterceptorId, number>>;
}

type ExecutionTotalsBySubject = Partial<Record<InteractionSubjectKey, SubjectExecutionTotals>>;

interface InteractionState {
  currentInteraction?: CurrentInteraction;
  dailyMemoryBySubject: DailyInteractionMemoryBySubject;
  executionTotalsBySubject: ExecutionTotalsBySubject;
}
```

`dailyMemoryBySubject` и `executionTotalsBySubject` находятся рядом с `currentInteraction`: выход не стирает память. В конце игрового дня **целиком** очищается дневная память, в том числе когда interaction ещё активен; долговременные totals сохраняются.

Запись создаётся только для нужного механизма: `perDay` требует дневного счётчика, `appearanceChance` — дневного boolean, `total` — долговременного счётчика. Если этих полей нет, вызовы «на всякий случай» не считаются. Если указаны оба лимита, используются обе карты. Начатая попытка Action, включая провал `check`, засчитывается; отказ до начала из-за требований или нехватки ресурсов — нет. Interceptor засчитывается только при фактическом запуске, включая провал его `check`.

Пример: `npc:bob` и `npc:carl` получают независимую память одного персонального Action, а два экземпляра POI с одним template — независимую память POI Action. Для общей кассы бара Action принадлежит **POI**: смена бармена не должна менять её subject. Содержательное состояние кассы при необходимости отражается в состоянии POI или квеста.

## 5. Дневной `appearanceChance`

После выполнения `conditions`, при первой допустимой актуализации Action или Interceptor с `appearanceChance`, runtime разрешает шанс и сохраняет **только результат** `appeared: true | false` по `subject + executableId`. Пока условий нет, броска нет. Повторный вход, смена Frame или time slot в тот же день использует прежний результат; новое значение шанса в этот день его не меняет. В конце дня результат очищается вместе с дневной памятью.

Для Action `false` означает скрытую кнопку. При `true` требования, стоимость и лимиты отдельно определяют, доступна ли видимая кнопка. Для Interceptor нет disabled-состояния: он либо включается в очередь, либо нет.

Бросок и запись должны происходить в runtime-операции актуализации, **не** в React render и не в чистом UI selector. При новом входе Interceptors сначала определяют, какой Frame будет показан, и могут изменить мир silent effects. Затем, **до первого показа выбранного Frame**, runtime бросает шансы его подходящих Actions. Поэтому бросок можно считать началом подготовки видимого Frame, но не началом входа ещё до обработки Interceptors. Если `conditions` впервые стали истинными при уже открытом Frame, бросок выполняется после соответствующей игровой операции.

## 6. Группы вариантов для UI

В `CurrentInteraction` нет сохранённого массива доступных Actions. Definitions находятся в `INITIAL_ACTIONS`, Frames содержат только `actionIds`, а квестовый slice содержит производные индексы ID. Runtime resolver читает текущий контекст, `activeFrameId` и актуальный игровой state. Он возвращает **отдельные группы по источнику**, чтобы UI мог показать slots карточками, POI-переходы на карте, а квестовые Actions со своей пометкой.

Схематичная форма результата (точные имена UI-типов уточняются при реализации):

```ts
interface ResolvedInteractionOptions {
  actions: {
    frame: UiAction[];
    poi: UiAction[];
    slot: UiAction[];
    personal: UiAction[];
    quest: UiAction[];
  };
  navigation: {
    npcSlots: UiNpcSlot[];
    poiTransitions: UiPoiTransition[];
  };
}
```

| Экран            | Заполняемые группы                                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Внутренний Frame | Только `actions.frame` из `frame.actionIds`                                                                                                                         |
| POI root         | `actions.frame`, `actions.poi`, `actions.quest` по `poiId`; занятые slots в `navigation.npcSlots`; переходы к родителю и дочерним POI в `navigation.poiTransitions` |
| Slot/NPC root    | `actions.frame`, `actions.slot`, `actions.personal`, `actions.quest` по `npcId`; возврат к текущему POI в навигации                                                 |

Квестовые Actions POI не подмешиваются в slot root, а персональные Actions NPC — в POI root. Порядок ID внутри авторских массивов сохраняется; UI самостоятельно решает расположение групп. Если один и тот же `actionId` попал в разные группы одного экрана, это ошибка данных, которую следует обнаружить при разработке, а не молча показывать дважды или смешивать группы.

Для Action resolver берёт `label` из definition: `conditions` и неудачный дневной `appearanceChance` скрывают вариант; невыполненные `requirements`, недостаточная стоимость или исчерпанный `executionLimit` оставляют его видимым, но disabled. Навигация — другой вид варианта UI: она собирается из runtime мира и текущего контекста, а не из `INITIAL_ACTIONS`. Interceptors также не входят в эти группы; они обрабатываются отдельной очередью до обычного root.

UI получает готовые группы и при выборе передаёт ID обычного Action в `performAction`, а навигационный вариант — в соответствующую команду перехода. В синхронной модели игры варианты обновляются после каждой операции, способной их изменить. Поэтому при нажатии **не выполняется повторный полный resolver** всех условий, требований и групп. Для начатой попытки динамическая стоимость разрешается один раз и используется при списании.

### Обычная навигация из состояния мира

- Занятый slot текущего POI даёт вариант перехода к его `slotId` и фактическому `npcId`; пустой slot варианта не даёт.
- Обнаруженный дочерний POI даёт переход из родителя. Необнаруженный или помеченный `pendingRemoval` POI не предлагается для нового входа.
- Закрытый по `schedule` POI остаётся видимым, но его переход disabled с пометкой «Закрыто»; до открытия взаимодействие с ним не начинается.
- Обычный возврат к родителю POI и выход из slot в текущий POI тоже выводятся из связей мира и текущего контекста. Такие постоянные варианты предоставляет навигация рантайма, например «Уйти» или «Перейти к дочернему POI». Авторский Action нужен, когда у выбора есть собственная сцена, проверка или effects; его `transition` может вести и в другой POI.

Доступность входа читается из runtime-состояния дочернего POI. `isEntryDisabled?: true` задаёт постоянную блокировку, а `entryDisabledDaysLeft?: number` — временную; отсутствие обоих полей означает, что дополнительной блокировки нет. Вместе с ними независимо работают `isDiscovered`, `schedule` и `pendingRemoval` по правилам `tension-force-exit-and-poi-entry.md`.

Обнаруженный POI с постоянной или временной блокировкой остаётся видимым, но его navigation option disabled. `pendingRemoval` по-прежнему полностью исключает новый переход. Interceptor фейсконтроля используется для сцены, которая начинается уже после допустимого входа, и не заменяет состояние доступа самого POI.

### Когда актуализировать группы

При входе сначала разрешаются Interceptors и выбирается фактически показываемый Frame; затем подготавливаются дневные броски для его впервые подходящих Actions и собираются группы, прежде чем UI их покажет.

После **любого** завершённого Action заново собираются **все** варианты окончательного видимого экрана. В root это все группы Actions и навигации; во внутреннем Frame — все Actions этого Frame. Cost, effects, квестовый stage и состояние мира могут повлиять на любой вариант, поэтому частичное обновление отдельных кнопок не используется. Если Action сменил контекст, собираются варианты уже нового контекста. Если при смене time slot возникла новая очередь Interceptors, она ждёт возврата из внутреннего Frame в root.

Тот же принцип применяется после иных игровых операций, меняющих видимый контекст или условия вариантов, например изменения occupancy и возврата из внешнего режима. Случайные результаты записывает runtime до показа; чистый UI resolver их только читает. Группы являются производными данными и не хранятся как отдельное состояние.

## 7. Исполнение Action: принятый порядок

Обычный Action выполняется как одна завершённая операция. UI опирается на актуализированные варианты и передаёт выбранный `actionId`; повторного вычисления всего списка и повторной проверки его видимости или `requirements` в начале `performAction` нет. Если ресурсов для показанного Action не хватало, он уже был disabled и попытка не начинается.

1. Разрешить динамические величины `cost` для этой попытки **один раз**. Денежные, предметные и stamina затраты списать авансом; `cost.time` пока сохранить как минуты для завершающего мирового действия. Попытка началась, поэтому она учитывается в `executionLimit`, даже если последующий `check` провалится.
2. Выполнить `check`, если он есть. По умолчанию проверку делает протагонист. Если проверки нет, использовать `result`; если есть — соответствующую ветку `onSuccess` или `onFail`. Взвешенный `ActionOutcome` выбирает один вариант. Отдельный выбор члена партии через UI можно добавить позднее.
3. Последовательно применить `effects` выбранного результата и записать его `narrative` в log исходного контекста. Log event хранит только один раз разрешённые narrative blocks; background, visual variant, overlay layout, role и display name отдельно не снимкуются.
4. Обработать `transition` результата после effects. Неуказанный transition оставляет текущий Frame. Если переход перемещает партию, вызвать соответствующее **мировое действие** `moveToPoi` вместо прямой перестановки контекста. Если перемещения нет, но есть `cost.time`, завершить операцию мировым действием `spendTime`/`rest` либо другим подходящим действием. Ему передаётся отложенное время; мировой переход также применяет обычные затраты по правилам перемещения. Один и тот же расход не списывается дважды.
5. По завершении мирового действия обработать предусмотренные изменения времени, schedule, occupancy и pending queue. Запланированный system `forceExit` исполнять только тогда, когда управление дошло до root, до его показа. Затем заново собрать все варианты экрана, который будет показан.

Это логический порядок; детали общего world executor и дневных тиков определяются при реализации соответствующих пунктов. Критично, что эффекты конкретного Action завершаются **до** общих последствий перемещения и изменения времени. Чистые динамические функции `check`, весов и effects читают состояние после авансового списания денег, предметов и stamina. Время до завершающего мирового действия ещё старое. Значение `cost.time` вычислено в начале и повторно не вычисляется.

Ветка проваленной проверки расходует ту же стоимость попытки, затем исполняет свои собственные narrative, effects и transition. Результат Action может запустить квест; если отложенное время пересечёт конец дня, новый квестовый таймер участвует в обычной дневной обработке без специального исключения.

### Переходы и лог

`ActionTransition` по-прежнему допускает `frame`, `root`, `currentPoi`, `parentPoi`, конкретный `poi`, `trade` и `combat`. Переход в другой POI **возможен** как результат авторского Action, в том числе квестового. Его не нужно запрещать или удалять из initial-контракта. Но обычные, часто встречающиеся перемещения лучше показывать явными вариантами навигации из состояния мира: их стандартное мировое действие автоматически начислит время, stamina и другие затраты пути. Авторский переход в другой POI возможен и должен пройти через ту же мировую операцию перемещения с соответствующими затратами; автор учитывает его смысл и дополнительные расходы Action. Таким образом `redBoar:leave` с `parentPoi` допустим как специальный Action, хотя обычное «Уйти» обычно даёт рантайм.

Во время effects текущие NPC и POI остаются исходными: `transition` выполняется позже, поэтому специальная копия «бывшей текущей цели» не требуется. Смена Frame внутри **того же** контекста сохраняет log. Переход к другому POI, между POI и slot/NPC или в другой slot/NPC начинает новый log. Смена POI ↔ slot/NPC при этом сохраняет текущий background; открываемый root Frame заменяет его только при наличии собственного `background`. Narrative результата записывается в исходном контексте; при смене контекста оно автоматически в новый log не переносится. Если текст нужен после перехода, автор размещает его в новом Frame.

`forceExit` проверяется только из **root**. Он не заменяет открытый внутренний Frame и не прерывает последовательность Frames. Если Action открывает Frame, тот разрешается до возврата в root; тогда проверяется `forceExit`. Если Action остаётся или сразу возвращается в root, проверка возможна после завершения Action и его мирового действия. Обновление вариантов относится к экрану, который в итоге действительно будет показан.

## 8. Save и восстановление — отложено

Save/load не входит в текущую и ближайшую миграцию. In-conversation save отсутствует, а `currentInteraction`, pending queue, background и log пока не обязаны быть сериализуемыми. Правила восстановления будут спроектированы отдельно и не ограничивают текущий runtime-контракт.

## Что остаётся для следующих пунктов

- Боевой transition и возврат из combat остаются за рамками этой миграции.
- Числовой порог `forceExit` остаётся балансным решением; базовая формула initial tension зафиксирована в `tension-force-exit-and-poi-entry.md`.
- Расширенный visual-variant resolver остаётся отложенным. Log уже зафиксирован как snapshot только разрешённых narrative blocks.

Это границы дальнейшей реализации, а не недостающие поля для согласованных пунктов 1–3.
