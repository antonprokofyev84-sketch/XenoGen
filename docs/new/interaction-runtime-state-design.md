# Interaction runtime

Состояние: [interactionRuntime.types.ts](../../src/types/interactionRuntime.types.ts).
Публичные команды и selectors: [interaction slice](../../src/state/gameSlices/interaction.ts).

## Контекст и варианты действий

Контекст хранит конкретный `poiId` и, для разговора, пару `slotId + npcId`.
`activeFrameId` указывает отображаемый Frame. Вход разрешается из фактической
позиции партии и актуального occupancy.
`slotId` и `npcId` присутствуют вместе. Смена контекста заменяет объект целиком,
чтобы идентификаторы места, роли и occupant не расходились между операциями.

Новый вход открывает root либо Frame события. Смена Frame внутри контекста
сохраняет его историю. Переход POI ↔ slot/NPC или к другому NPC создаёт новый
контекст; travel завершает исходный. При завершении NPC-контекста регистрируется
[встреча](npc-initial-data-design.md#встречи-и-отображаемое-имя).
Повторный подход начинает новый вход с актуальной очередью и root/Frame события;
оставленный внутренний Frame не восстанавливается. Дневные лимиты при этом сохраняются.

Источники Actions объединяются в таком порядке:

| Экран            | Источники                                   |
| ---------------- | ------------------------------------------- |
| POI root         | Frame → POI → quest index по `poiId`        |
| Slot/NPC root    | Frame → slot → NPC → quest index по `npcId` |
| Внутренний Frame | Собственные `frame.actionIds`               |

Занятые slots и переходы по дереву мира — отдельные варианты навигации.
При возврате из внутреннего Frame в root вступительный narrative повторно не добавляется.
Порядок ID внутри каждого источника сохраняется. POI-контент не подмешивается
в NPC root, а внутренний Frame использует только свои Actions, чтобы общие
возможности места не появлялись внутри авторской сцены.

После любого Action актуализируются все варианты окончательного видимого экрана:
расходы, effects и квестовый прогресс могут изменить соседние Actions и навигацию.
То же происходит после иных операций, меняющих условия, и возврата из внешнего режима.
Runtime заранее подготавливает дневные броски; UI resolver читает готовую память
и выводит группы, не записывая результаты случайности из React render.

## Актуальность контекста на границе root

Внутренний Frame продолжает начатую сцену с теми же `poiId`, `slotId` и `npcId`,
даже если за время действия NPC ушёл по расписанию или POI закрылся.
Мировое время, дневные эффекты, таймеры и occupancy обновляются обычным образом;
occupancy определяет доступность новых подходов, а не состав уже начатой сцены.

Перед показом обычного root проверяется актуальность контекста:

1. POI закрыт по расписанию — открыть `system:poiClosed` с сообщением и единственным
   Action `Leave`, выполняющим обычный travel к родителю.
2. POI открыт, но исходный NPC больше не занимает исходный slot — открыть
   `system:npcLeft` с сообщением и единственным Action `End talk`, возвращающим в POI.
3. Контекст актуален — обработать существующую очередь и показать обычные варианты.

Проверка предшествует вступительному тексту root и исполнению его очереди, включая
force exit. Она выполняется при открытии root и завершении шага, оставшегося в root.
Текст результата сначала подтверждается через Continue; затем выполняется
отложенный переход, если он есть, и завершается шаг.
Во внутренних Frames проверка расписаний откладывается до root.

Системный Frame выхода сохраняет фон и историю; обычные Actions и переключение
NPC/контекста недоступны. Подтверждение сообщения открывает единственную кнопку
выхода. Завершение NPC-встречи регистрируется при самом выходе, а не при обнаружении
ухода NPC. Повторный вход в POI при завершении разговора не создаётся.

Блокировки нового входа не означают закрытие уже начатого посещения.
Физическое удаление POI остаётся исключением: дневная очистка немедленно завершает
исходный interaction и эвакуирует партию по [правилам жизненного цикла POI](poi-initial-data-design.md#жизненный-цикл).

## Текст и история

`CurrentInteraction.currentEntry` содержит одну показываемую порцию разрешённых
narrative blocks. Поступающий текст Actions, Interceptors и Frames дополняет её
в исходном порядке. Имена и placeholders разрешаются при поступлении текста.

`log` содержит подтверждённые порции. Команда `continueInteraction`:

1. Переносит текущую порцию в `log`.
2. Очищает `currentEntry`.
3. Продолжает исполнение сценария; новый текст становится следующей порцией.

Подтверждение пустой порции ничего не делает. History отображает только `log`.
Режим Actions/narrative выводится из наличия текущей порции.
История сохраняет текстовый снимок, а не фон или состояние фигуры сцены.
При обычной смене контекста текст остаётся в истории исходного interaction;
описание назначения автор размещает в его Frame. Случай удаления источника
во время стоимости описан отдельно ниже.

## Исполнение Action

Исполнитель: [performAction.ts](../../src/systems/interaction/performAction.ts).

1. Публичная команда проверяет, что предыдущая порция подтверждена.
2. Executor один раз разрешает cost, проверяет оплату, списывает деньги,
   предметы и личную stamina, затем учитывает попытку.
3. Выполняет check и выбор результата. Числовые функции результата читают
   состояние после списания аванса.
4. Применяет effects и формирует текущую порцию narrative.
5. Проводит `cost.time` вместе с мировыми последствиями до публикации результата.
6. Выполняет transition сразу при пустом narrative либо после Continue.
7. Обрабатывает [очередь событий](interceptors-design.md), когда достигнут root,
   и актуализирует доступные варианты.

Провал check также расходует стоимость и лимит. Повторного resolver всех условий
при нажатии нет; executor повторно проверяет возможность оплаты.
Effects завершаются в исходном контексте до мировых последствий времени.
Если они активировали квест, его таймер участвует в конце дня, пересечённом
этой же стоимостью. Длительность перехода относится уже к следующему шагу сценария.

`interactionSlice.pendingTransition` хранит один обязательный переход и исходные
context IDs отдельно от текста. Пока он ожидает Continue, команды смены контекста,
нового Action, travel и продвижения времени блокируются. Инвентарь и просмотр
карты сохраняют взаимодействие. При продолжении переход извлекается до исполнения,
поэтому effects, расходы и броски попытки не повторяются.

## Время перехода

`cost.time` — длительность попытки. `transition.time` — полная длительность
последующего перехода в минутах:

- Для POI она заменяет обычное время пути; без поля действует обычный travel.
- Явный `0` означает мгновенный переход.
- Для локального перехода без поля длительность равна нулю.

Пример: попытка драки занимает 5 минут, затем показывается потеря сознания.
После Continue переход с `time: 240` проводит четыре часа и открывает описание пробуждения.

POI travel выполняет выход → изменение позиции партии → время → вход в конечный
POI. События прибытия разрешаются на конечное время. Локальный переход проводит
свою длительность и открывает целевой Frame в том же interaction; актуальность
расписаний проверяется только на границе root по правилам выше.

Если дневная очистка удалила источник во время `cost.time`, обязательный переход
завершается сразу. Разрешённый текст результата присоединяется к текущей порции
сохранившегося назначения. При удалении назначения используется surviving-parent
fallback. Цель `parentPoi` фиксируется до расхода времени.

## Память исполнения

Ключ памяти — `subject + executableId`: subject равен `poiId` для POI либо `npcId`
для разговора. Frames и slots не меняют адрес одной и той же записи субъекта.

- Daily memory хранит число попыток `perDay` и результат `appearanceChance`.
- Total memory хранит общий счётчик исполнений.
- Уход из interaction сохраняет обе памяти; конец дня очищает daily memory.
- `appearanceChance` бросается один раз за день после выполнения conditions,
  до показа вариантов. Изменение conditions актуализирует видимость без нового
  броска для уже проверенного executable. UI selectors читают готовый результат.

Например, два сундука внутри одного POI требуют разных Action IDs для независимых
попыток: переход между их Frames сохраняет один и тот же subject.

## Мировое время и конец дня

Оркестрация: [world slice](../../src/state/gameSlices/world.ts).
Для каждой пересечённой границы дня:

1. Выполнить дневные эффекты POI и обновить мировые счётчики.
2. Собрать истёкшие таймеры стадий, затем активных квестов; применить их effects.
3. Выполнить removal sweep помеченных POI.
4. Очистить daily interaction memory.

После всех прошедших дней один раз обновить schedules и occupancy конечного
слота времени. Завершение шага interaction отдельно проверяет его root;
само продвижение времени не исполняет очередь текущей сцены.
Жизненный цикл его очереди задаётся [правилами входа Interceptors](interceptors-design.md#вход-и-очередь).
Правила отдельных счётчиков заданы в документах [клеток](cell-initial-data-design.md),
[POI](poi-initial-data-design.md), [квестов](quest-system-design.md) и
[блокировок входа](tension-force-exit-and-poi-entry.md).
