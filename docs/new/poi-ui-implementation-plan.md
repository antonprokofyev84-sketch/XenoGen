## 1. Цель и границы

Перенести согласованную композицию макета в React-интерфейс игры: большая сцена, нижняя панель взаимодействия, портреты NPC слева, навигация справа и нижняя системная полоса. Использовать существующие Frames, Actions, occupancy, Interceptors и мировые команды.

В работу входят:

- новый `PoiView` для POI root, slot/NPC root и внутренних Frames;
- цикл «нарратив → клик/пробел → действия → результат»;
- чтение результата Action перед выполнением его перехода;
- один крупный NPC слева, шесть небольших портретных рамок в POI;
- категории и иконки действий, стоимость на кнопках, подсказки доступности;
- правая навигационная панель и заголовки внутренних сцен;
- история текущего взаимодействия;
- нижняя полоса со временем, time slot, заглушкой очков экспедиции и системными кнопками;
- подключение существующего экрана инвентаря с корректным возвратом в POI;
- тестовые изображения из макета и технические сценарии проверки.

Карта, экран персонажа/инвентаря, торговля и остальные экраны сохраняют существующее внутреннее устройство. Кнопки «Карта», «Отряд», «Настройки» в новой полосе являются заглушками. Из POI по-прежнему можно выйти в родительскую клетку через обычную навигацию мира; это отдельное действие от кнопки «Карта».

Не входят: новая карта района, переработка боя или торговли, управление отрядом, выбор исполнителя проверки, save/load, экономика очков экспедиции, новые механики усталости, мобильная версия, последовательный показ отдельных реплик и расширенные визуальные варианты NPC.

| Область | Решение |
| --- | --- |
| Базовый размер | 1600×900, композиция 16:9 |
| Масштабирование | Отсутствует: рамка 1 px, на большем экране поля, на меньшем прокрутка |
| Визуальный ориентир | Простые панели: полосатый фон и рамка 1 px; кнопки по CSS пользователя, нативный `corner-shape: bevel`; нижняя полоса цельная |
| Основная сцена | Один фон на всю игровую область, интерфейс поверх него |
| Портреты POI | Постоянные шесть рамок, три столбца × два ряда; занятые NPC идут подряд, пустые рамки в конце |
| Крупный NPC | Одновременно одна фигура слева; другой говорящий заменяет текущего |
| Нарратив | Весь текущий массив narrative целиком, без последовательного раскрытия отдельных реплик |
| Продолжение | Клик по свободной текстовой области панели или пробел |
| Подсказка продолжения | `[ КЛИК / ПРОБЕЛ ▶ ]` снизу слева в текстовой области |
| Кнопки действий | Общее поле, без заголовков групп; существующий порядок источников сохраняется |
| Категории | Разговор, задание, торговля, отдых, взаимодействие |
| Стоимость | Деньги и очки экспедиции — на самой кнопке, в скобках, когда значение действительно задано |
| Вероятность и время Action | Пока не показывать ни на кнопке, ни в подсказке |
| История | Только лог текущего interaction, как в существующем runtime |
| Внутренний Frame | Портреты и обычная навигация скрыты; справа можно показать название сцены |
| Рюкзак | Открывает существующий экран инвентаря/персонажа |
| Прочие системные кнопки | Заглушки, не меняют экран и состояние мира |

Для длинного текста в первой версии использовать прокрутку внутри текстовой области с отдельным местом под подсказку продолжения. Это технический способ разместить весь блок в фиксированной панели; автоматическую разбивку на страницы не вводить. Колесо прокрутки, выделение текста и отпускание мыши после выделения не должны подтверждать продолжение.

Количество NPC сверх шести пока не проектировать: в первом интерфейсе отображаются первые шесть доступных occupants. Если такой контент появится, он потребует отдельного решения. Не добавлять сейчас карусель, пагинацию или изменение occupancy ради визуального лимита.

## 4. Геометрия и оформление

`PoiView` получает сцену фиксированного размера 1600×900 без масштабирования. Внешняя оболочка центрирует её в большом окне и предоставляет прокрутку в меньшем. Внешняя рамка — 1 px. Размеры элементов не зависят от окна. Стандарт фигур и портретов уточнён в `visual-assets.md`.

Не переносить в игровую версию мобильные media queries демонстрационного HTML. Не менять геометрию из-за отсутствия NPC, малого числа действий или смены режима «текст/действия».

Контрольные размеры последнего макета, измеренные при 1600×900, округлены до пикселя:

| Элемент | X / Y | Ширина / высота |
| --- | --- | --- |
| Вся сцена | 0 / 0 | 1600 / 900 |
| Основная панель | 0 / 460 | 1600 / 355 |
| Правая область взаимодействия внутри неё | 536 / 513 | 1005 / 249 |
| Правая панель навигации, состояние разговора | 1200 / 23 | 371 / 219 |
| Нижняя системная полоса | 0 / 815 | 1600 / 86 |
| Полный холст крупной фигуры (уточнено после реализации) | 0 / 70 | По пропорциям файла / 1000; обрезан по y=803 |

Высота навигационной панели зависит от её содержимого; приведённые 219 px относятся к заголовку и одной кнопке возврата. Эти размеры служат проверкой переноса последнего макета, а не поводом для новой переработки композиции. Новая подсказка продолжения размещается внутри имеющейся текстовой области.

Оформление упрощено по последнему решению: `_poiTheme.scss` для простых полосатых панелей и `_gameButton.scss` для кнопок по CSS пользователя. Углы нативные (`corner-shape: bevel`), без `clip-path` и SVG-контуров. Прежние указания об удвоении рамок и декоративных уголках отменены. Актуальный контракт — `poi-ui-design.md`.

Стили новых игровых элементов ограничить классами экрана/компонентов. Не менять глобальный `Button` и стили существующей торговли или инвентаря ради этого экрана.

Слои сцены: фон → рамки панелей → содержимое панелей → крупная фигура NPC → системная полоса → подсказки/история → торговая модалка. Фигура не перехватывает клики и не закрывает правую область взаимодействия.

## 5. Категории Actions и стоимость на кнопке

### 5.1. Категория — поле Action

В `src/types/action.types.ts` добавить плоский `ActionCategory` и необязательное поле `category` в `InitialActionBase`.

| Значение | Подпись для автора | Общая иконка |
| --- | --- | --- |
| `dialogue` | Разговор | Облачко реплики |
| `quest` | Задание | Звезда |
| `trade` | Торговля | Весы |
| `rest` | Отдых | Кровать |
| `interaction` | Взаимодействие | Рука |

Отсутствующая категория означает `interaction`. UI сопоставляет категорию с одной общей иконкой. Иконки конкретных действий и анализ label для выбора иконки не нужны.

Действия из источника `quest` всегда отображаются со звездой. Для квестовых действий, которые появляются как собственные Actions внутреннего Frame, автор явно задаёт `category: 'quest'`: источник `frame` сам по себе не позволяет распознать квестовое назначение. Не определять его по названию ID и не строить дополнительный граф владения.

Порядок: `frame`, затем `poi` для POI root либо `slot` и `personal` для NPC root, затем `quest`. Внутри каждого источника сохраняется авторский порядок ID. Объединение для отображения не меняет источники, условия, субъект памяти и правила исполнения.

### 5.2. Действительная денежная стоимость

В `UiAction` передавать разрешённую денежную стоимость. При сборке варианта один раз получить объект `ResolvedActionCost` и использовать его для существующей проверки ресурсов и preview. Не вызывать одну и ту же числовую функцию отдельно ради подписи и disabled.

Примеры подписей:

- `Отдохнуть (10 мон.)`;
- `Купить выпивку (7 мон.)`;
- `Осмотреться` — без пустых скобок и нулевой стоимости.

Исполнитель по-прежнему один раз разрешает стоимость в момент начала попытки. Preview в UI не является вторым списанием и не заменяет проверку реального ресурса. Если открытие инвентаря меняет состояние, доступные варианты и preview актуализируются существующим selector.

Вероятность, сложность проверки и расход времени в первой версии не выводить. Не добавлять вычисление прогнозируемого шанса ради скрытого поля. Название навыка и объяснение невыполненного требования допустимы в подсказке; вероятность и цена времени туда не попадают.

### 5.3. Очки экспедиции пока являются демонстрационным отображением

Действующего ресурса `expeditionPoints` и его утверждённой стоимости в текущем `ActionCost` нет. Этот UI-этап не добавляет формулу, восстановление, расход, проверки доступности или замену личной stamina.

В отображающем компоненте кнопки предусмотреть необязательное значение стоимости очками экспедиции. В обычных runtime-вариантах оно пока отсутствует. Его внешний вид проверить в отдельном демонстрационном состоянии/техническом визуальном примере:

- `Разобрать завал (5 ОЭ)`;
- `Получить помощь (10 мон. · 3 ОЭ)`.

Не включать фиктивное списание в `performAction` и не помещать демонстрационные числа в действительный `ActionCost`. Когда механика будет утверждена, источник данных можно подключить к готовому отображению. До этого на обычной кнопке без значения ОЭ такой расход не изображается.

### 5.4. Подсказки и недоступность

Подсказка содержит необходимые предметы, видимые требования, причину недоступности и оставшиеся попытки при заданном лимите. Личная stamina остаётся действующей стоимостью и может объяснять блокировку; она не подменяется ОЭ и не добавляется в скобки рядом с деньгами.

Причины формировать при сборке `UiAction`, используя существующие проверки условий, стоимости и лимитов. По возможности расширить результат проверки, а не писать отдельную конкурирующую реализацию правил в React. Внутренние сюжетные `conditions` не раскрывать через подсказку скрытого действия.

Подсказка недоступной кнопки должна открываться при наведении и фокусе. Для этого использовать фокусируемую оболочку либо `aria-disabled` с блокировкой исполнения. Не рассчитывать на события обычного HTML `disabled`, которые могут не дать нужного поведения.

Кнопки размещаются общей сеткой из трёх колонок с естественным добавлением строк, без фиксированного `slice(0, 9)` и без растягивания кнопок на всю свободную высоту. Денежная подпись не обрезается. Длинный label может переноситься. Нужный рабочий объём проверить на 9, 12 и 15 действиях; для превышения высоты оставить техническую вертикальную прокрутку области действий, без увеличения внешней панели.

## 6. Состояние чтения и показ текста

Один лог выполняет роль истории; отдельно хранится то, что сейчас читает игрок. Не превращать весь накопленный `log` в текущий экран текста: иначе каждый Action будет повторно показывать предыдущий разговор.

Добавить в текущий interaction минимальное presentation-состояние:

- режим `narrative` или `actions`;
- текущие уже разрешённые narrative blocks;
- при необходимости единственное отложенное завершение Action.

Конкретные типы держать в `interactionRuntime.types.ts`. Удобно выразить два режима union, чтобы отложенное завершение не существовало у свободного выбора действий. Не вводить новый глобальный event bus, универсальную систему workflow или стек сцен.

В рамках одной завершённой операции входа все narrative-массивы, которые она добавила в текущий контекст, объединяются в одну отображаемую порцию в исходном порядке. Например, narrative Interceptor и narrative открытого им Frame читаются вместе. Отдельные строки и реплики внутри этой порции не требуют отдельных нажатий.

При входе в контекст с текстом открывается `narrative`. Без текста сразу открываются `actions`. После прочтения вступления показываются доступные действия этого же Frame. При появлении нового текста он становится текущим; старые blocks остаются в истории.

Повторное открытие root из внутреннего Frame того же контекста не должно автоматически добавлять его вступление. Для этого добавить явное различие входа и локального возврата в операции открытия root. Применение background и режима NPC при возврате сохраняется. Новый вход POI ↔ NPC остаётся новым контекстом с обычной обработкой входа и новым логом.

Если авторский результат не содержит narrative, не показывать пустую панель с обязательным дополнительным кликом.

## 7. Action с чтением результата перед переходом

Это основное изменение runtime. Сейчас `performAction` выполняет стоимость, check, effects, log, transition и обработку времени одной транзакцией. Новый вариант сохраняет порядок, но допускает паузу после narrative результата.

### 7.1. Начало попытки

1. Убедиться, что взаимодействие находится в режиме выбора действий, а не ждёт завершения другой попытки.
2. Разрешить стоимость один раз; проверить и списать деньги, предметы и личную stamina как сейчас.
3. Засчитать попытку в execution limits.
4. Один раз выполнить check и выбрать конкретный результат.
5. Применить его effects и добавить разрешённый narrative в лог исходного контекста.
6. Если narrative непустой, открыть режим чтения и сохранить только данные завершения: уже выбранный transition и отложенные минуты. Исходный контекст остаётся текущим.
7. Если narrative отсутствует, сразу выполнить завершение из следующего раздела.

После этого RNG, эффекты, авансовая плата и счётчики этой попытки больше не исполняются. Не хранить Action ID как инструкцию «выполни его повторно после клика».

### 7.2. Продолжение

Добавить публичную команду `continueInteraction()` в interaction slice. Для обычного чтения без отложенной попытки она открывает действия. Для результата Action она:

1. Забирает и очищает единственное ожидающее завершение до запуска его последствий.
2. Выполняет сохранённый transition через существующие local/world операции.
3. При travel передаёт отложенные минуты в `worldDraft.travelToPoi`, чтобы стоимость Action и время пути учитывались одним продвижением времени.
4. Без travel передаёт минуты существующей операции времени, как в текущем executor.
5. Завершает обработку времени, инвалидированных контекстов и pending events существующим порядком.
6. Актуализирует appearance chance и доступные варианты финального экрана.
7. Если завершение открыло Frame/контекст с новым текстом, показывает этот текст; иначе показывает действия.

`root`, `currentPoi`, `frame`, `poi`, `parentPoi` и открытие существующей торговли следуют одному правилу: непустой результат читается до перехода. После `currentPoi` начинается новый POI-контекст, после `root` сохраняется прежний лог. `trade` с narrative ждёт чтения, без narrative сразу открывает модалку. Саму торговую экономику не менять.

Если завершение или effects уничтожили текущий контекст, ожидающее продолжение очищается вместе с ним. Нельзя применить продолжение к другому NPC/POI после сброса. Полное завершение interaction также очищает это состояние.

### 7.3. Ограничения ввода во время чтения результата

До завершения попытки нельзя начать другой Action, переключить NPC или выполнить обычный переход. Видимые портреты/маршруты на root можно оставить на месте, но временно отключить их активацию. После прочтения без нового narrative они снова работают. Это не меняет физическую occupancy.

История и существующий инвентарь могут открываться поверх/вместо POI. Они не выполняют ожидающий переход; при закрытии возвращается та же стадия чтения. Изменение экипировки после уже выполненного check не пересчитывает полученный результат.

Публичная команда исполнения Action должна защищаться от повторного старта в режиме чтения. Для навигации из компонентов проверять тот же режим. Продолжение забирается ровно один раз; повторный вызов не повторяет плату или переход.

Нельзя переносить мировое время в React effect, таймер или обработчик анимации. За завершение отвечает domain-команда; React передаёт только намерение продолжить.

### 7.4. Interceptors и forceExit

Очередь `pendingEvents` не переименовывать и не смешивать с ожидающим завершением Action. Первая обслуживает автоматические события входа, второе — одну уже начатую попытку игрока.

Переходы Interceptors остаются частью существующей атомарной обработки входа. Для них не вводится новая пауза до transition: показывается уже разрешённый текст и фактически открытый Frame. Изменение касается чтения результата выбранного игроком Action.

Сохранить правило forceExit: он не прерывает внутренний Frame и исполняется при подходящем возврате в root. Проверка после Action выполняется после его отложенного завершения. Если изменилось время и occupant ушёл, используется существующая проверка валидности NPC-контекста.

## 8. NPC, портреты и имена

### 8.1. Сетка в POI

Источник — готовые `navigation.npcSlots` из resolver. UI не выбирает occupants, не делает chance roll и не обходит расписания заново. Идентификатор входа — существующая пара `slotId + npcId`.

Показать до шести занятых slots в текущем порядке resolver, затем добавить декоративные пустые рамки до шести. Никакой связи «номер визуальной рамки = slotId» не вводить.

Вход по портрету вызывает `enterSlotContext(slotId, npcId)`, а не travel. Подпись NPC получать единым существующим `resolveNpcDisplayName`: знакомый — имя, незнакомый — роль его slot. Сейчас `UiNpcSlot.name` берётся напрямую из initial NPC; при переделке привести этот путь к существующему правилу имени.

Если у занятого NPC нет портретного изображения, оставить доступную карточку с нейтральной заглушкой и подписью. Не превращать её в пустую декоративную рамку и не скрывать возможность разговора.

### 8.2. Одна крупная фигура

| Режим Frame | Во время текста | При показе действий |
| --- | --- | --- |
| `none` | Фигуры нет | Фигуры нет |
| `speaker` | Последний NPC, имеющий прямую реплику в текущем отображаемом нарративе | Фигура исчезает |
| `always` | Контекстный NPC; если в текущем тексте есть другой говорящий NPC, он временно заменяет контекстного | Контекстный NPC |

Для выбора speaker просматривать только текущий текст, а не весь исторический лог. Реплика протагониста не создаёт NPC-overlay. При `speaker` без подходящей NPC-реплики крупной фигуры нет. `always` без NPC-контекста остаётся ошибкой контента по существующему контракту.

В POI root обычная сетка занимает ту же левую область. Если текущий Frame допускает speaker и его narrative содержит реплику NPC, фигура временно заменяет сетку. При переходе к действиям `speaker` исчезает, и сетка возвращается. Во внутренних Frames сетка скрыта независимо от наличия фигуры.

Имя в области взаимодействия следует за реально отображаемым NPC. Когда фигура `speaker` исчезла, в разговоре можно сохранить заголовок основного собеседника, чтобы контекст оставался понятен. Не добавлять имя выступающей плашкой на рамке.

### 8.3. Изображения

Крупная фигура: `src/assets/npcs/<npcId>/full-body.webp` или `.png`, полный рост на прозрачном фоне. На экране персонажа и в диалогах сохранять относительный масштаб по росту и центрировать фигуру по обеим осям. Соотношение холста и численная сетка роста пока не утверждены. Независимый `portrait.webp` или `.png` — квадрат для карточки 100×100; рекомендуемый экспорт 200×200. Использовать отдельный resolver портрета рядом с `resolveNpcImage`. Подробности в `visual-assets.md`.

Портрет не вырезается автоматически из фигуры. Фигура должна иметь прозрачный фон, портрет — готовое кадрирование. Не добавлять пути к изображениям в изменяемый NPC state или slots.

Тестовые изображения из макета подключить обычными Vite imports/globs. Не переносить большие data URLs из демонстрационного HTML в TSX. Фоны технических Frames заменить реальными импортами этих тестовых файлов; расширенный выбор вариантов по роли/настроению пока не нужен.

## 9. Навигационная панель и внутренние Frames

На POI root правая панель показывает текущую локацию, возврат к родителю и обнаруженные дочерние POI. Неразрешённые переходы не генерируются отдельными UI-условиями.

Существующие состояния сохранить:

- скрытый или `pendingRemoval` POI не предлагается для нового входа;
- закрытый по расписанию виден как disabled с «Закрыто»;
- постоянная блокировка — «Вход недоступен»;
- временный запрет — «Вас сюда не пускают».

На NPC root панель содержит возврат в текущий POI. Кнопка вызывает `returnToPoiContext`, не перемещает партию и не начисляет время пути.

Во внутреннем Frame обычных маршрутов и портретов нет. Его авторские действия, включая уход/возврат, находятся только в поле Actions. Не дублировать их автоматически в правой панели.

В `InitialFrame` добавить необязательный `title?: LocalizedText`. Внутренняя сцена с title показывает его справа. Если title отсутствует, использовать название текущего места без технического Frame ID. В этой панели нет списка кнопок, когда resolver не дал маршрутов.

Обычные переходы к родителю/детям по-прежнему вызывает `world.actions.travelToPoi`. Восемь направлений — проверочный пример, не жёсткое ограничение. При длинном списке панель ограничивается свободной высотой над нижней панелью, внутри доступна прокрутка. Не обрезать массив переходов ради макета.

В исходных fixtures есть и authored Actions ухода, и derived navigation. Дубликаты в демонстрационном root убрать корректировкой технического контента, когда authored уход не имеет собственного смысла. Не фильтровать UI по ID `leave` или типу transition: авторский переход со сценой/стоимостью остаётся обычным Action.

## 10. История, системная полоса и возврат из инвентаря

### 10.1. История

Кнопка «История» остаётся в заголовке взаимодействия. Открывает окно поверх сцены с разрешёнными narrative blocks текущего `log`. Закрытие кнопкой, Escape и кликом вне окна; ввод не передаётся подлежащей сцене.

История не запускает checks, effects, переходы и повторное разрешение narrative. Просмотр не меняет режим текущего чтения. На смене POI ↔ NPC и travel лог сбрасывается как сейчас. Архив завершённых разговоров, запись выбранных labels и отдельные визуальные snapshots не добавляются.

### 10.2. Нижняя полоса

Показывать день/часы из существующего игрового времени и название текущего time slot через `resolveTimeOfDay`. Использовать `START_DATE` из constants вместо ещё одной захардкоженной начальной даты. Подписи time slots хранить в одном месте.

Очки экспедиции: фиксированная подпись без ресурса, например `Очки экспедиции: —`. Она демонстрирует размещение показателя и ничего не списывает. Постоянные деньги, HP, stamina и портреты отряда в системную полосу на этом этапе не добавляются.

«Рюкзак» открывает существующий `characterDetails`. «Карта», «Отряд», «Настройки» выглядят как системные кнопки-заглушки и не инициируют переходов, времени или отмены чтения. Существующие кнопки отдыха карты не переносить в POI автоматически.

### 10.3. Возврат из существующего экрана

В UI state добавить минимальные команды открытия `characterDetails` с запоминанием вызывающего экрана и закрытия с возвратом. Один return screen достаточен; стек навигации не требуется.

Убрать жёсткое `goToScreen('strategicMap')` из кнопки закрытия `InventoryPanel`. Открытие из карты возвращает на карту, открытие из POI — в тот же `PoiView`. Перед входом в инвентарь не вызывать `endInteraction` или `enterPoiContext`.

Presentation-состояние чтения хранится вместе с interaction, поэтому размонтирование `PoiView` не теряет показанный текст, ожидающий transition и стадию чтения. Деньги/экипировка после закрытия могут обновить доступность будущих действий, но уже полученный результат не пересчитывают.

Торговая модалка сохраняет существующее управление через `isTrading`. Пока она открыта, обработчик продолжения POI не активен.

## 11. Предлагаемое разделение компонентов

Новые компоненты располагать внутри `features/PoiView`, кроме общей системной полосы, если её действительно подключают на других экранах. Не вводить универсальную UI-платформу.

| Компонент | Ответственность |
| --- | --- |
| `PoiView` | Сборка экрана, фон, порядок слоёв, существующий `TradeModal` |
| `SceneViewport` | Размер 1600×900, рамка 1 px, центрирование и прокрутка без масштаба |
| `NpcPortraitGrid` | Шесть рамок и выбор готового occupied slot |
| `NpcFigure` | Единственная выбранная фигура, без собственной игровой логики |
| `InteractionPanel` | Общий заголовок и переключение текста/действий |
| `NarrativeView` | Вывод текущих blocks и подсказка клика/пробела |
| `ActionList` / `ActionButton` | Общая сетка, иконка категории, стоимость, подсказка, disabled |
| `PoiNavigation` | Готовые маршруты либо заголовок внутреннего Frame |
| `InteractionHistory` | Окно текущего лога |
| `GameBottomBar` | Время/time slot, заглушка ОЭ и системные кнопки |

Существующие `DialogPanel`, `DialogOptions`, `ImagePanel` можно заменить этими компонентами или переименовать с учётом их новой ответственности. После переключения удалить неиспользуемую старую вёрстку и SCSS, не поддерживать два активных PoiView.

## 12. Этапы реализации и критерии завершения

### Этап 1. Контракты и минимальные presentation-данные

Изменить `action.types.ts`, `frame.types.ts`, `interactionRuntime.types.ts`, `resolveOptions.ts`, `presentation.ts`, при необходимости `conditions.ts` и development validator.

Добавить категорию Action, title Frame, действительный денежный preview и данные объяснения недоступности. Определить состояние текста и единственного отложенного завершения. Визуальный лимит NPC и общая сетка действий не меняют underlying данные.

Критерий: типы описывают согласованный UI, все существующие definitions работают с defaults, значение денег берётся из существующего cost, правила источников и скрытия не изменены.

### Этап 2. Завершение Action после чтения

Изменить `performAction.ts`, `interactionState.ts`, slice взаимодействия и операции очистки. Вынести существующее завершение попытки в функцию, используемую как немедленным, так и отложенным путём. Добавить `continueInteraction`.

Разделить внешний вход во root и локальный возврат для narrative. Обработать переходы, время, forceExit, смену occupants и отсутствие текста.

Критерий: все виды переходов выполняются после чтения результата, проверки/плата/effects ровно однократны, нет пустого чтения, root-вступление не повторяется при локальном возврате.

### Этап 3. Сцена и статическая компоновка

Собрать `SceneViewport`, фон, рамки основной/правой панелей, область портретов и прямую системную полосу. Подключить тестовые assets, перенести утверждённые материалы и кнопки.

Критерий: при 1600×900 композиция соответствует измеренному ориентиру с уточнёнными размерами фигур и портретов; при смене текста и действий их область не сдвигается. При уменьшении окна появляется прокрутка, размер элементов сохраняется.

### Этап 4. Портреты, фигура и навигация

Подключить `navigation.npcSlots`, переходы и единый NPC presentation resolver. Добавить portrait resolver, корректную подпись незнакомых NPC и title внутреннего Frame.

Критерий: работают POI root, NPC root и внутренний Frame; сетка всегда из шести рамок; фигура одна; заблокированные места сохраняют причины; ordinary navigation не позволяет обойти авторскую внутреннюю сцену.

### Этап 5. Текст, действия и история

Подключить текущий текст, клики, пробел, вывод Action costs, категории и подсказки. Реализовать историю. Предотвратить всплытие клика по Action в обработчик только что открытого текста.

Игнорировать повторные `keydown` с `event.repeat`. Пробел не прокручивает страницу и не продолжает сцену, когда открыт инвентарь, история, торговля или активен ввод в поле. Клики по кнопкам, истории и другим контролам не считаются кликом по тексту.

Критерий: один пользовательский ввод соответствует одному шагу; надпись «КЛИК / ПРОБЕЛ» стоит снизу слева; деньги и демонстрационный формат ОЭ помещаются на кнопке; время и шансы нигде не появились.

### Этап 6. Системная полоса и инвентарь

Подключить время/time slot, подпись ОЭ и «Рюкзак». Исправить возврат из `characterDetails` через UI state, проверить старый вход из карты. Заглушки не получают реальную навигацию.

Критерий: после рюкзака восстанавливается ровно тот экран и стадия чтения, из которых его открыли; инвентарь и торговля визуально/функционально продолжают использовать существующие компоненты.

### Этап 7. Проверки, очистка и документация

Пройти сценарии ниже, выполнить production build в полной рабочей копии и development authoring validator. Удалить неиспользуемые компоненты и стили прежнего PoiView.

Обновить профильные документы миграции, перечисленные в разделе 14. Внести именно принятые изменения UI/presentation, сохранив прежние границы остальных систем.

## 13. Проверки результата

Автоматические проверки нужны прежде всего для нового разрыва Action на два шага. Не писать тесты, проверяющие буквальное совпадение CSS или воспроизводящие каждую строку разметки. Если Vitest уже есть в полной рабочей копии, использовать его и существующий injectable RNG; не добавлять отдельную тестовую инфраструктуру.

### Domain и orchestration

1. Платный Action с narrative и переходом: до continue деньги/предметы/stamina и счётчик попытки списаны один раз, позиция/время ещё не изменены; после continue переход и минуты применены один раз.
2. Проверка с двумя исходами: ожидание чтения и повторный continue не вызывают RNG или effects повторно.
3. Action без narrative завершается сразу; Action без transition показывает результат и затем возвращает действия.
4. `root` из внутреннего Frame не повторяет вступительный narrative, но продолжает ожидающую очередь событий.
5. `currentPoi` и travel создают новый лог только при своём фактическом переходе; до continue исходный результат доступен для чтения.
6. Смена time slot при завершении корректно обновляет occupancy и закрывает утративший валидность NPC-контекст; запланированный forceExit следует существующим правилам.
7. Завершение/сброс interaction удаляет отложенную попытку; она не выполняется в новом контексте.
8. Денежный preview и доступность используют один разрешённый cost на проход resolver; скрытые conditions не превращаются в видимые disabled-кнопки.

### Ручные визуальные и пользовательские сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| POI с 0, 1, 3 и 6 NPC | Шесть одинаковых рамок, occupants подряд, свободные в конце |
| NPC без portrait/figure | Разговор доступен; нейтральная заглушка карточки, отсутствие фигуры не ломает композицию |
| `none`, `speaker`, `always`, другой speaker | Одна корректная фигура либо её отсутствие; просмотр истории не меняет её |

| 1600×900, окно больше, окно меньше | Размеры сохраняются; в большом окне поля, в маленьком доступна прокрутка ко всем краям |

## 15. Результат реализации

Игрок входит в POI, читает его текущий текст и по клику/пробелу получает действия. В POI видит шесть портретных рамок, справа — доступные места. Выбор NPC открывает разговор в той же композиции с одной крупной фигурой слева. Выбор Action показывает уже полученный результат; его переход выполняется после чтения. Во внутренних сценах обычная навигация скрыта. История, торговля и существующий инвентарь открываются без потери текущей стадии взаимодействия.

Деньги отображаются в цене на кнопке, формат очков экспедиции подготовлен для подключения будущего ресурса. Время и вероятность проверок остаются частью механики, но пока не показываются в информации об Action.
