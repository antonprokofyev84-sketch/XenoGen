# Статические квесты

Формат: [questContent.types.ts](../../src/types/questContent.types.ts),
состояние: [questRuntime.types.ts](../../src/types/questRuntime.types.ts).
Реестр — `src/data/initial/quests.ts`, исполнение — `src/state/gameSlices/quest.ts`.

## Модель прохождения

Квест хранит сюжетный прогресс, а действия игрока исполняются обычными Actions.
Стадия определяет текущую задачу и добавляет входные Actions/Interceptors нужным
NPC и POI. Внутренние ответы разговора принадлежат открываемому Frame.

Стадию меняет тот Action, который действительно завершает задачу. Открытие
разговора с Леной ещё не означает, что игрок узнал местонахождение курьера:
переход выполняет ответ внутри разговора, после которого сведения получены.
Одна стадия может давать несколько путей: спросить Лену, подкупить охранника
либо самостоятельно найти следы. Они могут сходиться на одной стадии или
приводить к разным ветвям.

## Definition и начало

Квест содержит `name`, основную `description`, optional `isHidden`, общий `timeLimit`
и map стадий. Обязательная начальная стадия — `initialStage`.
Стадия задаёт optional `title`, `description`, собственный `timeLimit` и привязки
Actions/Interceptors по владельцам.

Все статические квесты создаются при новой игре: `status: 'initial'`,
`stageId: 'initialStage'`, пустые vars, основная задача первой записью журнала.
Привязки initialStage позволяют показать предложение через обычный Action.
`setQuestStage` переводит квест из initial в active и запускает выбранную стадию.

Обычное предложение устроено так: входной Action открывает Frame поручения,
«Принять» выполняет `setQuestStage`, «Отказаться» возвращает в root. Если отказ
оставил квест в `initialStage`, предложение доступно позднее. Для немедленного
начала без подтверждения входной Action может сам сменить стадию.
Другие источники начала — Interceptor или `onExpire` таймера `initialStage`:
они применяют тот же effect смены стадии.

| Status                 | Runtime и участие в игре                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| `initial`              | `initialStage`, vars и журнал уже существуют; действуют её привязки, записи скрыты в журнале |
| `active`               | Текущая рабочая стадия, её привязки, vars и таймеры                                          |
| `completed` / `failed` | Сохраняются status, видимость и журнал; stage, vars, таймеры и привязки удаляются            |

Завершённый статический квест остаётся записью истории. Повторное прохождение
проектируется отдельным квестом, а генерация повторяемых поручений —
[динамическими квестами](ideas.md#динамические-квесты).

## Привязки и индексы

`actionIdsByTarget` и `interceptorIdsByTarget` содержат ID definitions из общих
реестров и адресуют конкретный `npcId` или `poiId`.
Это ID экземпляров: `templateId` и `slotId` владельцами квестовых привязок
не являются. Событие именно в определённом slot задаётся через
[контент slot](poi-initial-data-design.md#npc-slots) с квестовыми conditions.

```ts
stages: {
  initialStage: {
    actionIdsByTarget: { keeper: ['missingCourier:offer'] },
  },
  searchCellar: {
    description: 'Search the cellar for the courier.',
    actionIdsByTarget: { cellar: ['missingCourier:search'] },
  },
}
```

`questSlice` хранит производные индексы по владельцам. Для initial участвует
initialStage, для active — текущая стадия. При смене стадии старые привязки
удаляются, новые добавляются; при завершении остаётся только удаление.
Индексы строятся при новой игре и обновляются инкрементально, чтобы при каждом
разговоре не обходить все квесты. Источником истины остаются definitions и runtime.
Изменение vars влияет на conditions, сохраняя состав кандидатов индекса.
Один executable ID предоставляется одному root-источнику контекста;
дубли — ошибка авторских данных.

Общие правила [Actions](action-initial-data-design.md) и
[Interceptors](interceptors-design.md) используются напрямую.

## Переменные и progression effects

Vars — map значений `boolean | number | string`. Отсутствующее значение — `undefined`.
Например, `notEquals: true` выполняется и для отсутствующего флага; заранее
записывать все флаги как `false` не требуется.
Они описывают конкретное состояние задачи: найденная улика, выбранная сторона,
выполненные параллельные поручения. Синтаксис чтения vars описан в
[условиях Actions](action-initial-data-design.md#видимость-доступность-и-расходы).

| Effect                        | Результат                                                  |
| ----------------------------- | ---------------------------------------------------------- |
| `setQuestVar`                 | Установить значение по ключу                               |
| `snapshotDefeatedCount`       | Сохранить число побед над типом врагов как baseline        |
| `setQuestStage`               | Перейти на стадию, добавить её описание, установить таймер |
| `setQuestJournalVisibility`   | Показать или скрыть запись квеста                          |
| `completeQuest` / `failQuest` | Завершить квест с соответствующим статусом                 |

В одном блоке effects допустим максимум один lifecycle-effect на конкретный квест:
`setQuestStage`, `completeQuest` или `failQuest`. Возврат в уже текущую стадию
сохраняет её таймер и журнал. Завершённый runtime хранит статус, видимость и журнал.
Изменение стадии, vars и baseline работает для `initial`/`active`;
видимость журнала меняется в любом статусе. Повторный сюжетный эпизод оформляется
новым stage ID, даже если его задача похожа на ранее пройденную.

### Параллельные задачи

Для задачи «расспросить Боба и Лену, затем отчитаться» разговоры устанавливают
`askedBob: true` и `askedLena: true`. После своей беседы каждый входной Action
скрывается через condition `notEquals: true` на соответствующий флаг.
Action отчёта остаётся видимым, но его requirements требуют оба флага:

```ts
requirements: [
  { type: 'questVar', questId: 'missingCourier', key: 'askedBob', equals: true },
  { type: 'questVar', questId: 'missingCourier', key: 'askedLena', equals: true },
];
```

Переменные позволяют выполнить разговоры в любом порядке. Стадию меняет
последующий Action отчёта; установка флага сама по себе её не переключает.

### Победы после принятия поручения

При принятии задачи «победить десять рейдеров» сохраняется baseline, затем
квест переходит на рабочую стадию:

```ts
effects: [
  {
    type: 'snapshotDefeatedCount',
    questId: 'huntRaiders',
    key: 'defeatedAtStart',
    enemyTypeId: 'raider',
  },
  { type: 'setQuestStage', questId: 'huntRaiders', stageId: 'hunt' },
];
```

Action сдачи использует `defeated` с `min: 10` и
`baselineFromVar: { questId: 'huntRaiders', key: 'defeatedAtStart' }`.
Если до принятия общий счётчик был 37, сдача станет доступной при 47.
Отдельный квестовый счётчик после каждого боя не нужен: проверяется разница
между общей статистикой и снимком. Без baseline проверялись бы все прежние победы.

### Зависимости между квестами

Факт, нужный зависимому квесту, записывается в его vars до завершения исходного:
после complete/fail vars исходного квеста удаляются. Runtime зависимого статического
квеста существует с начала игры, поэтому такую запись можно сделать до его принятия.
Например, сохранить `lenaAgreed: true` в следующем квесте, затем завершить текущий.
Для фактов, нужных многим независимым системам, предусмотрено отдельное
[проектирование фактов мира](ideas.md#poi-и-локализация-контента).

## Журнал

`journalEntries` хранит разрешённые строки: основную задачу и описания посещённых
стадий. Текущая стадия может дать короткий title. Скрытый квест продолжает работать
и добавлять записи; `isHidden` управляет только видимостью журнала.
Descriptions разрешаются через `resolveText()` один раз при добавлении записи;
журнал показывает авторскую историю, а условия доступности сдачи остаются в Actions.
Показываются квесты со `status !== 'initial'` и `isHidden === false`.
Default `isHidden` — `false`. `setQuestJournalVisibility` с `isVisible: true`
раскрывает запись, сохраняя стадию и status; у initial-квеста она всё ещё скрыта.
Завершение сохраняет выбранную видимость.
При `timeLimit.showInJournal` показывается соответствующий оставшийся срок;
при истечении в журнал добавляется «Срок истёк».

## Таймеры

`QuestTimeLimit` задаёт положительные `days`, `onExpire` и `showInJournal`.
Общий `questDaysLeft` уменьшается только при active; `stageDaysLeft` работает
также для initialStage. Истечение запускает effects: следующий этап, завершение
либо другой авторский результат.
Само истечение не означает провал: `onExpire` явно задаёт последствие.
Например, срок поручения может перевести квест на стадию конфронтации с NPC,
а не завершить его. Таймер `initialStage` может активировать отложенное предложение.
Смена стадии сохраняет общий срок квеста. Истёкший счётчик удаляется, его `onExpire`
срабатывает один раз. Новый стадийный срок создаётся при входе на стадию.

На дневном тике сначала уменьшаются таймеры текущих стадий всех работающих квестов,
затем общие таймеры active-квестов. Effects собираются и применяются после обоих
проходов в том же порядке. Поэтому созданный этим переходом таймер новой стадии
начнёт уменьшаться на следующем тике. Одновременно истёкшие таймеры одного квеста
должны иметь совместимые lifecycle-results.

Место этой фазы в общем дне — [мировое время](interaction-runtime-state-design.md#мировое-время-и-конец-дня).
