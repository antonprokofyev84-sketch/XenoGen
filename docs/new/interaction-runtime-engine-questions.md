# Interaction Runtime and Engine Design

## Назначение документа

Документ отделяет runtime, Zustand, execution flow и UI/presentation от initial-структур. Он синхронизирован с `migration-decisions.md`, `interaction-runtime-state-design.md` и `tension-force-exit-and-poi-entry.md`; старые варианты ниже не являются альтернативными контрактами.

Нерешённые балансные или внешние вопросы помечаются явно. Всё остальное в документе описывает принятый runtime-контракт.

Актуальный контракт initial Actions описан в `action-initial-data-design.md`. Ниже отдельно отмечены принятые правила и вопросы реализации. Имена новых runtime helpers и расположение полей служат ориентиром, а не готовой схемой Zustand. Разделы про NPC из последней переданной версии документа сохранены.

Термин `Scene` пока не используется. Возможное переименование `Interaction` рассматривается отдельно.

## 1. Уже принятые runtime-ограничения

### Interaction context

Текущая идея контекста:

```ts
poiId: PoiId;
slotId?: SlotId;
npcId?: NpcId;
```

```text
только poiId                  → POI-контекст
poiId + slotId + npcId        → slot/NPC-контекст
```

Отдельный discriminant `type` пока не требуется. Нужно обеспечить инвариант, что `slotId` и `npcId` либо присутствуют вместе, либо оба отсутствуют.

### Повторный вход

При новом входе в POI прежний `activeFrameId` не восстанавливается.

```text
начало interaction
→ прочитать дневное состояние
→ собрать и выполнить очередь Interceptors входа
→ после её завершения показать обычный root
```

Authored Interceptor может открыть Frame события либо применить silent effects. `forceExit`, вызванный состоянием interaction, является system item той же pending-очереди, но не authored Interceptor definition.

Дневная interaction memory сохраняется до конца дня, включая счётчики Actions, результаты случайной видимости и дневной tension NPC. Ключ executable memory — subject + executableId; структура зафиксирована в `interaction-runtime-state-design.md`. При выходе из interaction дневное состояние не сбрасывается.

### Narrative при переходах

Предварительно принято простое различие:

```text
переход вперёд → narrative целевого Frame отображается
возврат назад  → narrative root Frame повторно не отображается
```

Полноценная история Frames и `seenFrameIds` пока не требуются.

### Actions UI

Actions нового Frame становятся доступными сразу. При смене Frame UI может:

```text
скрыть предыдущие Actions короткой анимацией
→ показать новые Actions короткой анимацией
```

Показ Actions не ждёт окончания последовательного reveal narrative blocks.

### Conditions

Conditions проверяются на уровне Actions. Сам Frame не получает condition. `conditions` скрывают Action, `requirements` оставляют его видимым, но disabled. Оба массива работают как AND. Недостаточная стоимость и исчерпанный дневной лимит также блокируют выполнение. Случайная видимость хранится отдельно от conditions (раздел 11).

Interceptors имеют собственные `conditions`, потому что определяют участие автоматического события во входе, но не являются частью Frame definition.

### Background

При travel в другой POI или полном завершении interaction текущий background сбрасывается. После этого первый Frame может установить новый background либо оставить экран без изображения.

Внутри одного interaction Frame без `background` сохраняет текущий background. Переключение POI root ↔ slot/NPC context начинает новый log, но сохраняет background; новый root Frame заменяет его только при наличии собственного значения.

### Закрытый POI

На первом этапе закрытый POI не запускает interaction. Элемент перехода остаётся видимым, но disabled и помечен как закрытый.

## 2. Что можно использовать как пример из старого interaction slice

Существующий `interactionSlice` создан для другого дизайна и будет почти полностью переписан. Он не задаёт структуру новой runtime-памяти. Из него можно использовать как примеры отдельные приёмы:

- `CurrentInteraction`;
- `interactionMemoryById` с очисткой в конце дня;
- `effectiveRelation`, `initialTension` и `tension`;
- `tradeAttempts`;
- двухфазное выполнение: resolve вне draft, применение внутри `set`;
- `EffectManager` и effect summaries;
- сохранение уже разрешённых narrative blocks в log events;
- `interactionDraft`, который вызывается из атомарного travel pipeline;
- планирование system `forceExit` после полного выполнения Action;
- отдельное состояние trade modal.

Что именно останется после переписывания, определяется при проектировании нового runtime; сохранять текущие maps и типы только ради совместимости не требуется.

## 3. Миграция services → Frames/Actions

Сохраняется основа существующего interaction slice. Направление замены:

| Сейчас                              | Целевая модель                                         |
| ----------------------------------- | ------------------------------------------------------ |
| services                            | Definitions из `INITIAL_ACTIONS`                       |
| services текущего контекста         | Root content из Frame, POI/slot/NPC и quest action map |
| `service.executedTimes`             | `executionLimit.perDay` для subject + actionId         |
| `performService`                    | `performAction`                                        |
| Замена services при force exit      | Переход в forceExit Frame                              |
| Специальные проверки Action ID в UI | Общий обработчик transition                            |

В текущем interaction нужны `activeFrameId`, текущий background, log и контекст POI/slot/NPC. Количество выполнений и сохранённая видимость принадлежат дневной памяти субъекта. Не нужно хранить независимые счётчики одновременно в definition, Frame и interaction.

Итоговое размещение полей в store, хранение либо вычисление разрешённых Action IDs и способ доступа к дневной памяти будут определены при реализации runtime. Initial definitions не мутируются.

## 4. Interaction context switching

Переход между POI root и slot root не перемещает партию и выполняется отдельной runtime navigation command.

Схема открытия slot:

```text
сохранить состояние текущего POI-субъекта
→ установить slotId и npcId
→ загрузить дневную память NPC
→ получить либо впервые рассчитать дневные relation/tension NPC
→ начать новый log, сохранив текущий background
→ открыть slot root Frame
```

Схема возврата:

```text
сохранить дневную память NPC
→ очистить slotId и npcId
→ восстановить состояние POI-субъекта
→ начать новый log, сохранив текущий background
→ открыть POI root без повторения его narrative
```

POI ↔ slot/NPC всегда начинает новый log. Background при этом не сбрасывается: root Frame нового контекста применяет собственный background либо наследует текущий. Navigation option вызывает runtime-команду context switching; обычный `performAction` используется только для authored Actions.

Occupant может измениться при переходе в новый time slot. Schedules и occupancy обновляются до пересборки Interceptors. Если текущий NPC больше не занимает slot, его interaction-контекст завершается, и runtime возвращается к актуальному POI-контексту.

## 5. Дневная interaction memory

### Ключ субъекта и Action

Принято: для Action достаточно **subject + actionId**.

- В POI-контексте subject — конкретный `poiId`, а не `templateId`.
- В slot/NPC-контексте subject — конкретный `npcId`.
- `frameId` и `slotId` в ключ счётчика не входят.

Например, строковые ключи могут иметь форму `poi:<poiId>` и `npc:<npcId>`. Это способ не смешивать пространства IDs; окончательно можно выбрать один map либо отдельные maps.

Два encounter с одним template имеют разную память. Одинаковое персональное действие у разных NPC также учитывается отдельно. Один Action в нескольких Frames одного subject использует один счётчик. Для двух независимых сундуков у одного subject автор задаёт разные Action IDs; определение можно создать общей фабрикой.

### Что живёт до конца дня

- Счётчики начатых попыток Actions, включая провал check.
- Результаты `appearanceChance`, включая отрицательный результат.
- Дневные interaction-данные, уже существующие в системе: tension, trade attempts и соответствующая память субъекта.

Выход из POI, смена Frame и повторный вход не сбрасывают эти данные. В конце дня дневная память очищается, в том числе для открытого interaction. Нельзя очистить только неактивную memory, оставив активные счётчики прошлого дня.

Это правило не сбрасывает накопительные `timesMet`, `visitedTimes`, постоянные отношения и состояние квестов. Они принадлежат своим механикам.

При новом входе восстанавливается дневное состояние, но не старый `activeFrameId`. Перед сборкой authored Interceptors runtime вызывает `ensureNpcDailyTension()` для slot/NPC-контекста. Если tension уже достиг порога, `scheduleForceExit` заменяет authored snapshot до его исполнения. Затем pending queue может открыть Frame; при пустой очереди открывается обычный root.

При первой встрече с NPC за день initial tension использует исправленную базовую формулу текущей реализации:

```ts
const randomOffset = Math.floor(random() * 41) - 20;
const initialTension = clamp(-effectiveRelation + randomOffset, 0, 100);
```

Старый знак `effectiveRelation + randomOffset` был ошибочным: хорошее отношение не должно повышать напряжение. Числовой threshold `forceExit` остаётся балансной константой.

### Долговременные последствия

`executionLimit.total` использует долговременный счётчик и не очищается вместе с дневной памятью. Если одноразовость уже выражается состоянием квеста, предмета или POI, общий лимит можно не указывать. Завершённый временный POI можно пометить на удаление; подробности в разделе 15.

### Что ещё относится к реализации

1. Окончательная схема maps и доступ активного interaction к памяти.
2. Как конкретный Action изменяет память другого субъекта, если этого требует сюжет.
3. Как конфликт с отдельным NPC влияет на весь POI. Это не автоматическое следствие `role`: нужные последствия должны определяться правилами действия/взаимодействия.

## 6. Interceptors при входе и system `forceExit`

Interceptors полностью заменяют прежнюю идею entry rules для автоматических событий входа:

- постановочных событий POI;
- первого знакомства с NPC;
- активных квестовых эпизодов;
- случайных событий;
- событий, относящихся к конкретному slot.

Сам Frame остаётся пассивным. Interceptor обычно открывает первый Frame события, а дальнейший многошаговый эпизод проходит через обычные Actions. Interceptor без перехода может применить silent effects и сразу продолжить очередь.

### Источники

```text
вход в POI
→ poi.interceptorIds
→ questInterceptorIdsByTarget[poiId]

вход в slot/NPC
→ slot.interceptorIds
→ npc.interceptorIds текущего occupant
→ questInterceptorIdsByTarget[npcId]
```

Так покрывается прежний кейс exact slot rule без превращения slot в `QuestTargetId`. Базовый slot Interceptor может иметь квестовые `conditions`, если должен быть активен только на определённом состоянии квеста.

### Очередь входа и смена time slot

При реальном переходе из родительского контекста в дочерний runtime собирает authored items в `pendingEvents`, проверяет `conditions`, дневной результат `appearanceChance` и execution limits и сортирует их по `priority`. Отсутствующий `priority` равен `100`.

Перед исполнением конкретный ID сначала удаляется из очереди, затем повторно проверяются его актуальность и `conditions`:

- если проверка больше не проходит, ID молча отбрасывается;
- если результат не содержит перехода, effects применяются и очередь продолжается сразу;
- если результат открывает Frame, очередь приостанавливается;
- возврат из Frame в root того же контекста продолжает очередь;
- переход в parent, другой POI, бой, завершение interaction или более глубокий дочерний контекст удаляет очередь родителя;
- Interceptors, ставшие доступны после создания списка, ждут следующего отдельного входа или пересборки после смены time slot.

Каждый ID присутствует в одной собранной очереди один раз. Одинаковый `InterceptorId`, пришедший из нескольких источников, считается ошибкой данных; runtime не выполняет дедупликацию.

Для slot/NPC каждый новый подход из POI root является отдельным входом. Обычный `{ type: 'root' }` внутри того же контекста не пересобирает Interceptors.

Если Action или Interceptor переводит время в новый time slot, старая очередь удаляется. Изменение времени выполняется атомарно: при пересечении нескольких time slots промежуточные очереди не строятся. После достижения конечного времени runtime:

1. обновляет schedules и occupancy;
2. проверяет актуальность текущего interaction-контекста;
3. собирает новую очередь для актуального контекста;
4. запускает её сразу, если открыт root, либо сохраняет до следующего возврата в root, если игрок остаётся во внутреннем Frame. Перед запуском такой queue в slot/NPC-контексте после очистки дневной memory runtime вызывает `ensureNpcDailyTension()`.

Если переход текущего Action ведёт в parent, другой POI, дочерний контекст, бой или завершает interaction, очередь прежнего контекста удаляется. Дневной результат `appearanceChance` при пересборке не перебрасывается.

После смены time slot тот же Interceptor может снова попасть в новую очередь. Если событие не должно повторяться, его результат меняет содержательное состояние его `conditions` либо использует подходящий `executionLimit`; отдельный список обработанных IDs не вводится. Например, первое представление NPC использует `timesMet === 0` и `executionLimit.total: 1`, а успешный фейсконтроль должен выдать состояние доступа, включая при необходимости временный пропуск.

### System `forceExit`

`forceExit`, возникающий из текущего состояния interaction — например, после достижения tension threshold, — является system item общей pending-очереди, а не authored Interceptor входа.

```text
Action полностью выполнен, включая transition и мировое действие
→ trigger требует forceExit
→ scheduleForceExit идемпотентно заменяет authored-остаток очереди
→ внутренний Frame, если он открыт, разрешается до root
→ в root system item открывает reserved Frame либо применяет fallback
```

System `forceExit` существует только для slot/NPC tension и использует reserved Frame `<templateId>/<slotId>:forceExit`. При отсутствии Frame context возвращается в текущий POI. POI-context force exit не реализуется. Внешний переход Action, удаление POI или invalidation slot/NPC context очищает запланированный item; system `forceExit` не создаёт второй несовместимый transition поверх уже покинутого контекста.

## 7. Transition model и граница slices

### Принятая форма initial-данных

```ts
type ActionTransition =
  | { type: 'frame'; frameId: FrameId }
  | { type: 'root' }
  | { type: 'currentPoi' }
  | { type: 'parentPoi' }
  | { type: 'poi'; poiId: PoiId }
  | { type: 'trade' }
  | { type: 'combat' };
```

Transition находится в `ActionResult`. Его отсутствие означает остаться; отдельный `stay` не нужен.

- `frame` меняет Frame в текущем контексте. NPC/POI не выводятся из Frame ID.
- `root` возвращает к root текущего POI- или slot/NPC-контекста.
- `currentPoi` заканчивает slot/NPC-контекст и открывает root текущего POI без travel и нового посещения. Из POI-контекста это возврат в его root.
- `parentPoi` перемещает партию к родителю текущего POI.
- `poi` перемещает партию в явно указанный POI.
- `trade` открывает торговлю, сохраняя текущий Frame.
- `combat` запускает бой.

Root POI находится по `templateId`, root slot — по `<templateId>/<slotId>`. Обычный возврат к root внутри того же контекста не пересобирает Interceptors, а продолжает текущую очередь. Если очередь была заменена из-за смены time slot во внутреннем Frame, именно новая очередь начинает исполняться при возврате в root. Runtime ID конкретного POI остаётся источником контекста и памяти.

### Где обрабатывать

Принятое направление — единая точка `performAction(actionId)` в interaction slice. React-компоненты передают выбор, а не разбирают конкретные IDs `leave`, `trade` и т. п.

Текущий код уже использует две фазы: чтение и resolve вне `set`, применение через draft внутри `set`. Эту основу можно сохранить:

1. Разрешить и применить результат Action.
2. Внутренний Frame transition выполнить через interaction helper.
3. Для внешнего перехода после завершения текущего `set` вызвать публичный action соответствующего slice — например, `get().world.actions.travelToPoi(targetPoiId)`.

Не вызывать публичный action с новым `set` изнутри незавершённого `set`. Текущий world travel pipeline уже отвечает за завершение старого interaction, перемещение и открытие нового. Его не нужно копировать в interaction slice или напрямую вызывать world drafts оттуда.

Направление вызовов не требует отдельной сущности-команды для каждого перехода. Реализация может разделить чтение, draft-изменения и внешний world action на несколько технических шагов, но обязана сохранить принятый порядок одной Action-операции и не создавать вложенных `set`. Background и narrative остаются данными Frames/logs, а не внешних transitions.

### Бой и возврат

Action только запускает бой. Принятый flow победы: послебоевой Frame с добычей, затем отдельный Action ухода. Уход может пометить завершённый encounter на удаление и выполнить `parentPoi`.

Сейчас предполагается бесконечная вместимость рюкзака и кнопка «Взять всё». Частичный вынос добычи не требует отдельной архитектуры на этом этапе.

Как combat slice хранит контекст возврата, выбирает послебоевой Frame и передаёт добычу, обсуждается отдельно. Специальный initial-флаг `removePoiOnVictory` не вводится.

### Границы реализации

- Порядок Action, внешнего transition и пересечённых дневных тиков уже зафиксирован; конкретное разбиение на store-транзакции не должно его менять.
- Передача параметров запуска боя и контекста возврата из combat slice остаётся частью отдельного combat design.

Открытие slot выполняет runtime navigation command. Приоритет `forceExit` отдельно не выбирается: Action завершается полностью, а system item существует только пока исходный контекст остаётся актуальным и исполняется при достижении root.

## 8. Interaction log и presentation state

Log event хранит только разрешённые narrative blocks. При его создании `resolveText()` и dynamic narrative разрешаются один раз:

```text
speakerId: '$npc' → конкретный npcId
{$npc}            → имя знакомого NPC либо название роли незнакомого NPC
```

В log должны попадать уже разрешённые blocks, чтобы последующее изменение occupancy, знакомства или роли не меняло старый текст. Background, visual variant, overlay layout, role и display name отдельным presentation snapshot не сохраняются.

Смена Frame внутри одного POI- либо slot/NPC-контекста сохраняет log. Переход POI ↔ slot/NPC, переход в другой slot/NPC либо travel в другой POI начинает новый log. Narrative результата остаётся в log исходного контекста и автоматически в новый не переносится.

## 9. NPC overlay runtime

Initial Frame использует зафиксированные режимы:

```ts
type NpcDisplayMode = 'none' | 'speaker' | 'always';
```

```text
none    → не показывать NPC overlays
speaker → показывать speaker текущей реплики
always  → постоянно показывать npcId slot-контекста
```

Default — `speaker`. Использование `always` без `npcId` является ошибкой initial-данных.

Режим `none` не показывает overlays, даже если в narrative есть speaker. Это уже заданная семантика режима.

Зафиксированная baseline-композиция:

```text
NPC режима always → постоянно справа
другой speaker    → временно слева
always NPC говорит → остаётся справа, но визуально выделяется
```

Точная анимация появления/скрытия speaker и расширенные visual variants могут уточняться на UI-этапе, не меняя этого контракта композиции.

## 10. Root content resolution

Runtime возвращает отдельные группы по источнику, а не один смешанный UI-массив:

```ts
interface ResolvedInteractionOptions {
  actions: {
    frame: UiAction[];
    poi: UiAction[];
    slot: UiAction[];
    personal: UiAction[];
    quest: UiAction[];
  };
  navigation: {
    npcSlots: UiNpcSlot[];
    poiTransitions: UiPoiTransition[];
  };
}
```

Внутренний Frame получает только `actions.frame`. POI root получает frame/poi/quest Actions и navigation из мира; slot root — frame/slot/personal/quest Actions и возврат в текущий POI. UI самостоятельно решает, показывать ли группы кнопками, карточками, портретами или иным способом.

`conditions` и дневной appearance result определяют видимость; `requirements`, cost и execution limits — disabled-state. Обычные parent/child/slot transitions строятся из runtime мира и выполняются navigation commands. После любого завершённого Action заново собираются все варианты фактически показываемого экрана. При нажатии повторного полного resolver/recheck Action нет.

## 11. Исполнение Actions, чистые функции и случайность

### Read context

Функции числовых параметров получают курируемый read-only facade и идентификаторы текущего контекста: `poiId`, `slotId?`, `npcId?`, `frameId`, итоговые region levels текущего POI, affection/effective relation текущего NPC, tension и доступ к quest vars. Сырой `StoreState` content-функциям не передаётся. Частые проверки региона используют декларативный `regionLevel` condition.

Функция возвращает число и не вызывает RNG, `set`, effects или world actions. Общий resolver различает число и функцию. Формула может использовать параметры региона, отношения, квесты и другие данные из state.

Нужно сохранить возможность выбрать исполнителя stat/skill check: в старом `performService` уже есть аргумент `characterId` с default протагониста. Это runtime-контекст выполнения; собеседник `npcId` не становится автоматически исполнителем проверки. Окончательный тип аргументов определяется при реализации.

### Разные виды случайности

| Механизм                            | Когда разрешается                                           | Срок результата          |
| ----------------------------------- | ----------------------------------------------------------- | ------------------------ |
| `appearanceChance`                  | При первом подходящем показе для subject/action в этот день | До конца дня             |
| `check.chance` или stat/skill check | При начатой попытке                                         | Результат этой попытки   |
| Веса `ActionOutcome[]`              | При выборе результата начатой попытки                       | Один выбранный результат |

`appearanceChance` и `check.chance` находятся в `0..1`. Веса относительные, неотрицательные, с положительной суммой; выбирается ровно один вариант по сумме весов. Веса не являются независимыми chance rolls. Функции весов и difficulty разрешаются для текущей попытки.

Отдельный механизм `autoSuccess`/`autoSuccessRelation` не переносится. Чистая функция `check.chance` может вернуть `1` для гарантированного успеха или `0` для гарантированного провала. Обычный Action без проверки использует `result`.

### Случайная видимость на день

Рабочее правило первого броска:

1. Проверить обычные `conditions`. Если они не выполнены, Action скрыт; новый appearance roll не нужен.
2. Для пары subject + actionId найти сохранённый результат `appearanceChance` текущего дня.
3. Если записи ещё нет, один раз разрешить шанс, выполнить бросок и сохранить boolean.
4. Если запись есть, использовать её, включая `false`.
5. После видимости проверить requirements, стоимость и дневной лимит для состояния disabled.

Отсутствующая запись и сохранённое `false` — разные состояния. Не проверять наличие cache через truthiness. При отсутствующем `appearanceChance` случайность не ограничивает показ; запись можно не создавать.

Возврат во Frame, повторный вход, rerender и обновление selector не перебрасывают видимость. Изменившийся в тот же день threat также не изменяет уже полученный результат. При этом обычные conditions продолжают скрывать/открывать Action по актуальному state. Сохранённый результат используется снова, если условия вновь выполнены.

### Порядок одной попытки

UI передаёт `actionId` из уже актуализированного набора. В начале `performAction` не выполняется повторный полный resolver присутствия, `conditions` или `requirements`.

1. Зафиксировать исходный контекст и один раз разрешить динамические величины cost.
2. Авансом списать money/items и личную stamina протагониста; учесть начатую попытку. `cost.time` сохранить для завершающего мирового действия.
3. Выполнить check, если он есть, и выбрать один result соответствующей ветки или weighted outcome.
4. Последовательно применить effects выбранного результата.
5. Добавить в log только разрешённые narrative blocks результата.
6. Выполнить transition. Для внешнего перемещения вызвать стандартное world action и передать ему отложенный `cost.time` вместе с обычными затратами самого перемещения, не списывая один расход дважды. Если перемещения нет, но есть `cost.time`, вызвать стандартное `spendTime`/`rest` action.
7. Обработать последствия времени, schedule, occupancy и pending queue, затем пересобрать все варианты фактически показываемого экрана.

Невыполненные requirements, лимит или недостаточная стоимость уже сделали показанный Action disabled, поэтому попытка не начинается. Провал начатого check расходует ту же стоимость и увеличивает счётчик.

Динамическая стоимость разрешается один раз для попытки: проверять достаточность одной суммы и списывать другую нельзя. Числовые аргументы выбранного результата также должны применяться в том значении, которое executor разрешил для этой попытки; уточнение общей read/write-фазы относится к реализации.

Action сначала применяет effects, затем добавляет уже разрешённые narrative blocks в log и только после этого выполняет transition. Это не означает ожидание окончания показа текста: отдельная очередь, блокирующая transition до прочтения narrative, не вводится. Обычный Action выхода может вообще не иметь narrative.

Если effect требует `forceExit`, runtime планирует system item. Action и его transition завершаются полностью; item исполняется только если исходный контекст всё ещё актуален и управление дошло до его root. Поэтому второй несовместимый внешний transition не создаётся.

### Effects и время

Executor реализует только закрытый v1-каталог из `migration-decisions.md`. Quest effects всегда несут явный `questId`; structural POI effects используют явный `poiId` либо утверждённый `'$currentPoi'`; `modifyTension` относится к текущему NPC subject. Варианты изменения affection/reputation текущей или явно указанной цели остаются отложенными и не переносятся из старого `resolveInteractionEffects` без отдельного сценария.

При глобальных квестовых Actions необходимо однозначно передать quest target. В initial-примерах указан `questId`; имя Action или Frame не является способом автоматически определить цель эффекта.

Стоимость времени обрабатывает executor через существующую систему изменения времени, а не React-компонент. Изменение времени одного Action атомарно: сначала вычисляется конечное время и выполняются необходимые дневные тики, затем один раз обновляются schedules и occupancy и пересобирается очередь Interceptors конечного time slot. Промежуточные очереди не запускаются.

При реализации необходимо сверить один существенный случай: стоимость или travel пересекает конец дня, а текущий POI уже помечен на удаление. До перехода нужно располагать необходимыми исходными данными, например `parentId`; нельзя полагаться только на чтение удаляемого объекта после очистки.

### Побег из forceExit encounter

Видимость возможности уйти и вероятность успешного ухода принадлежат Action. Автор выбирает `appearanceChance` либо `check.chance` в зависимости от желаемого поведения, а Frame только содержит ссылку.

Для формулы берётся согласованная величина: raw-параметры клетки — числа `0..999`, включая дробные значения; конечные уровни POI — целые `0..9`. Формула побега — настройка контента/баланса, а не новое поле Frame.

### Детали реализации, не меняющие контракт

1. Точные TypeScript-интерфейсы `ActionContext`, selectors и будущего выбора исполнителя check.
2. Техническое разбиение resolve/draft/world action без вложенных store-транзакций при сохранении принятого порядка.
3. Физическое размещение дневных counts и appearance cache в slices; вся дневная память, включая память активного interaction, очищается общей фазой конца дня.

Срок жизни log уже определён: Frames одного контекста сохраняют его, а POI ↔ slot/NPC и travel в другой POI начинают новый. Каталог v1 effects закрыт в `migration-decisions.md`; новые relation effects не добавляются без отдельного сценария.

## 12. Известные расхождения старого slice с новой моделью

При будущей миграции нужно учесть:

- `poiType` должен быть заменён актуальной связью через `templateId`;
- `hasOwner` больше не соответствует новой slot-модели;
- старые local spot intros больше не соответствуют slots внутри POI;
- `services` и `InteractionServiceState` должны быть заменены Actions и их runtime counts;
- `applyForceExitServicesDraft` должен выбирать Frame, а не заменять services;
- специальная проверка `serviceId === 'trade'` должна быть заменена общим flow;
- cost сейчас списывается только при success, хотя для новой Action-модели принято списание при начатой попытке независимо от результата check;
- `timeCost` присутствует в типе, но не применяется в показанном `performService`;
- `buildEntryInteractionLog` должен уступить место разрешению начального Frame и его narrative;
- `interactionMemoryById` сейчас хранит массив service states, который потребуется заменить дневным runtime-состоянием Actions по subject + actionId;
- старые `autoSuccessRelation`, неявная relation-derived difficulty и fallback проверки не переносятся как отдельные поля: гарантированный исход выражается `check.chance`, а действие без проверки — `result`;
- отказ из-за недостатка ресурсов не должен превращаться в провал check с учётом попытки;
- случайная видимость должна кешироваться на весь день, а не на вход во Frame;
- закрытие interaction не сбрасывает дневную память, а новый вход не восстанавливает старый Frame;
- физическое удаление завершённых временных POI заменяется пометкой и общей очисткой в конце дня.

## 14. NPC runtime: расписание, встречи и визуальные assets

Эта секция фиксирует решения, которые возникли при проектировании `InitialNpc`, но не должны храниться в его immutable initial-описании.

### Resolved schedule и occupancy

`baseSchedule` NPC содержит `work`. Расписание задаёт время, а POI slot — место работы:

```text
baseSchedule[currentTimeOfDay] === work
И NPC указан в candidateNpcIds рабочего slot либо назначен в него runtime assignment
И рабочий POI открыт
→ NPC допустим только для work slots этого рабочего контекста

baseSchedule[currentTimeOfDay] === work, но подходящего открытого workplace нет
→ NPC остаётся неразмещённым, без fallback в freeTime/home
```

Resolved schedule строится глобально для NPC, независимо от того, посещён ли рабочий POI. Static candidate допускается максимум в одном work slot; runtime assignment supersedes static work membership. Поэтому NPC с текущим состоянием `work` заранее исключён из `freeTime`/`home`, а подходящий открытый work POI резервирует его для рабочей группы до фактического разрешения occupancy.

Runtime placement использует resolved state:

```text
work     → только work slots
freeTime → только freeTime slots
home     → только home slots
hidden   → NPC нигде не размещается
```

Если NPC имеет resolved state `work`, но не занял ни одного рабочего slot, он остаётся неразмещённым и не откатывается к `freeTime` либо `home`.

Фактическая occupancy при этом разрешается лениво только для POI, в который вошёл игрок. Невходимый POI не выполняет chance rolls и не получает cache фактических occupants: он лишь резервирует работающих NPC через resolved schedule. При первом входе в POI в time slot его occupants выбираются и кешируются; повторный вход использует cache. Источник текущего размещения — occupancy slice; NPC initial-объект не получает `currentPoiId`, `slotId`, `role` или `workplaceId`.

Построенные комнаты базы используют ту же систему. Назначение хранится отдельно от immutable template candidates по `poiId + slotId`; оно не изменяет `candidateNpcIds`. Совместимый назначенный NPC занимает slot без `chance`, а при его недоступности slot остаётся пустым без candidate fallback.

Внутренняя форма `resolvedSchedulesByNpcId` и occupancy indexes выбирается при реализации, но разделение глобального resolved schedule и lazy actual occupancy является частью контракта.

### Times met

В runtime `timesMet` всегда нормализован в число. Он увеличивается при выходе из взаимодействия с NPC в недочерний контекст, но не чаще одного раза за календарный день:

```ts
if (npc.lastDateMet === null || diffCalendarDays(npc.lastDateMet, currentTime) > 0) {
  npc.timesMet += 1;
}

npc.lastDateMet = currentTime;
```

Повторные взаимодействия с тем же NPC в тот же день счётчик не меняют. Простое присутствие NPC в occupancy, его отображение на экране или открытие POI root встречей не считаются.

Отдельная дневная map не нужна: используется уже согласованное runtime-поле `lastDateMet`. Для POI аналогичная проверка `visitedTimes` выполняется через `lastTimeVisited`.

Отдельный `isKnown` не нужен:

```ts
const isKnown = npc.timesMet > 0;
```

### Визуальные assets NPC

Визуальные данные отделены от `InitialNpc`. В initial NPC сейчас нет `image`, `directory`, `visualSet` или `visualId`.

По умолчанию visual resolver ищет визуальную запись по `npcId`. Это избегает дублирования вида:

```ts
visualSet: 'bob'; // не хранится рядом с NPC bob
```

Assets подключаются средствами Vite:

```text
одиночный известный asset → статический import
группа вариантов          → import.meta.glob
```

Asset import возвращает разрешённую Vite строку URL. Сырые пути к папкам не хранятся в runtime NPC state.

Baseline использует `import.meta.glob` и соглашение `src/assets/npcs/<npcId>/default.webp`.

В будущем resolver может получать `npcId` и runtime-контекст изображения:

```text
role текущего slot
экипировка или броня
состояние и повреждения
настроение или отношение
```

Отложены расширенная структура visual registry, приоритет вариантов, lazy/eager стратегия групп и optional `visualId` для общего набора. Visual variant в log event не сохраняется: log содержит только разрешённые narrative blocks.

## 15. Завершённые POI и централизованное удаление

### Принятое решение

В runtime POI вводится пометка `pendingRemoval?: true`: объект должен быть удалён при обработке конца дня. В initial placement/template это поле не добавляется.

Единственная операция пометки работает рекурсивно:

```ts
function markPoiForRemoval(poiId: PoiId): void {
  const poi = poiById[poiId];
  if (!poi) return;

  poi.pendingRemoval = true;

  for (const childId of poi.childPoiIds) {
    markPoiForRemoval(childId);
  }
}
```

Она немедленно устанавливает `pendingRemoval` самому POI и всем его потомкам. Операция идемпотентна: повторная пометка уже помеченного узла ничего не ломает.

Action ставит пометку через effect, а выход выполняет обычным transition:

```ts
result: {
  effects: [{ type: 'markCurrentPoiForRemoval' }],
  transition: { type: 'parentPoi' },
},
```

Это оставляет POI и его `parentId` физически доступными во время завершения действия и выхода. Effect не удаляет объект посреди применения результата. Дополнительные `afterTransitionEffects`, `removePoiOnVictory`, `removeWhenEmpty` и отдельный transition удаления не нужны.

Конкретные имена поля и effect обозначают выбранный контракт, а не уже существующую реализацию в проекте.

### До конца дня

Помеченный POI считается завершённым: его не предлагают для нового посещения, не используют для новых взаимодействий и не запускают для него `onDayPass`. Если партия ещё внутри, обычный выход остаётся возможным. Пометка не должна блокировать сам Action/transition, которым игрок покидает этот POI.

Все вложенные POI помечаются одновременно с родителем. Это необходимо именно на этапе логической пометки: непомеченный потомок иначе мог бы выполнить собственный `onDayPass` до физического удаления.

Комментарий для будущих нестандартных Actions: прямое перемещение извне в потомка помеченного POI должно учитывать завершённость родителя. Отдельную сложную систему для такого редкого случая сейчас не проектируем.

### Когда помечать

Пометка выражает завершение конкретного контента. Для тайника это может быть Action «Взять всё и уйти». Для encounter — Action ухода из послебоевого Frame после получения добычи. Если получение добычи и уход разделены, место пометки определяется их flow; физическое удаление всё равно отложено.

Текущий план — бесконечная вместимость рюкзака и «Взять всё». Механику частичного выноса сейчас не вводим.

Пустота инвентаря не является универсальным критерием: у торгового encounter можно купить всё, не завершив encounter. Бой также не получает отдельный флаг удаления «на победе».

`executionLimit.perDay` может запрещать повторное получение добычи до ухода. Для двух разных объектов у одного subject используются разные Action IDs. Если удаление самого POI уже выражает одноразовость, `executionLimit.total` только ради этого не нужен.

### Порядок конца дня

Физическое удаление выполняется ровно один раз в самом конце пайплайна. До этого все причины удаления только рекурсивно ставят `pendingRemoval`.

1. Зафиксировать список POI, существующих к началу дневного тика. POI, созданные позднее effects этого же `onDayEnd`, в текущем тике не обрабатываются.
2. Обойти этот список и выполнить `onDayPass`. Непосредственно перед каждым POI повторно проверить `pendingRemoval`; помеченный узел пропустить.
3. Уменьшить `lifetimeDaysLeft` непомеченных POI. Если срок достиг `0`, сразу вызвать рекурсивный `markPoiForRemoval` для всего поддерева.
4. Обработать остальные зарегистрированные world-owned дневные счётчики. В частности, уменьшить `explorationDaysLeft` клеток и `entryDisabledDaysLeft` POI; истечение разведки оставляет `0`, а временная блокировка при нуле удаляет поле. Новые счётчики подключаются к этой общей фазе со своим zero-state rule.
5. Пройти таймеры стадий квестов и добавить их `onExpire` в массив effects.
6. Пройти общие таймеры активных квестов и добавить их `onExpire` следом.
7. Выполнить собранные квестовые effects по порядку. Любой effect удаления POI на этом шаге также только рекурсивно ставит `pendingRemoval`.
8. Одним общим проходом физически удалить все помеченные POI и очистить их зависимости.
9. Полностью очистить дневную память Actions и Interceptors; долговременные total-счётчики не очищать.
10. После обработки всех пересечённых границ дня и достижения конечного времени один раз построить global resolved schedules, разрешить необходимую occupancy конечного time slot, проверить текущий interaction-контекст и собрать его новую pending queue.

Обычный временный POI со сроком жизни `1` сначала выполняет effects последнего дня и только после этого помечается. POI, помеченный до своей очереди `onDayPass`, как и все его рекурсивно помеченные потомки, дневные effects не выполняет.

Если одна операция времени пересекает несколько дней, этот пайплайн выполняется отдельно для каждого прошедшего дня. Если конец дня достигнут посреди Action или travel, физическую очистку нужно запускать в стабильной точке после завершения текущей команды, чтобы не уничтожить используемый ею interaction-контекст.

Уменьшение срока разведки клетки не означает удаление клетки. Сохраняется её согласованная семантика актуальности разведки.

### Единая очистка зависимостей

К моменту очистки всё поддерево уже помечено. Общая процедура одним проходом удаляет помеченные узлы и согласованно обновляет карту POI, `childPoiIds` оставшихся родителей и связанные runtime-данные: инвентари, occupancy и POI-память, если они существуют для удаляемого объекта. Если помечены и родитель, и ребёнок, очистка не должна пытаться рекурсивно удалить ребёнка второй раз.

Дневная память самостоятельного NPC не становится собственностью POI только потому, что NPC занимал его slot. Удаление POI не означает автоматического удаления NPC.

Централизация делает порядок удаления предсказуемым, но сама по себе не исправляет оставшиеся ссылки. Это ответственность общей процедуры удаления зависимостей. Её состав нужно сверить с актуальными slices при реализации, без добавления дополнительных initial-полей.

### Требования к реализации

- Если время пересекает конец дня внутри Action или travel, команда заранее сохраняет минимальные исходные данные, необходимые для завершения уже выбранного перехода, включая parent target удаляемого POI.
- Единый removal helper обязан очистить все фактически существующие зависимости удалённых POI; перечень проверяется по актуальным slices при реализации.
- Resolved schedules, occupancy конечного time slot, валидация interaction-контекста и pending queue выполняются после всех дневных тиков текущей операции времени, а не между промежуточными днями.
