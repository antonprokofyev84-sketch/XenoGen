# Interceptors

Формат: [interceptor.types.ts](../../src/types/interceptor.types.ts).
Реестр: `src/data/initial/interceptors.ts`. Исполнитель —
[interactionState.ts](../../src/systems/interaction/interactionState.ts).

## Назначение и границы

Interceptor — автоматическое событие при входе во взаимодействие с POI или NPC.
Например, после истечения срока поручения Мара должна начать конфронтацию при
следующем разговоре. Обычный Action игрок может просто не нажать; Interceptor
откроет сцену до появления обычных вариантов root.

Разделение ответственности:

- Interceptor определяет, какое событие запускает система.
- Frame задаёт сцену события.
- Actions внутри Frame описывают решения игрока и их стоимость.

У Interceptor есть `conditions`, `appearanceChance`, `executionLimit`, `priority`
и один вариант `result` / `check`. Результат содержит narrative, effects и
необязательный переход во Frame. Все conditions должны выполняться; неподходящее
событие пропускается. Условия появления и проверки используют
[общий контракт Actions](action-initial-data-design.md).

`label`, `requirements` и `cost` относятся к выбираемым игроком Actions.
Например, Interceptor открывает сцену охранника, а оплату прохода описывает Action
подкупа внутри неё. Если выбор не нужен, событие может применить effects и
продолжить очередь без открытия отдельного Frame.

Область действия — конкретный interaction-контекст. Истечение квестового таймера
может изменить стадию сразу, но привязанный к Маре Interceptor начнёт разговор
только при следующем подходе к ней. Событие, которое должно произойти независимо
от посещения NPC или POI, запускается через соответствующую мировую обработку,
например [истечение таймера квеста](quest-system-design.md#таймеры).

## Источники

| Контекст | Источники                                                            |
| -------- | -------------------------------------------------------------------- |
| POI      | `interceptorIds` шаблона POI и quest index по `poiId`                |
| Slot/NPC | `slot.interceptorIds`, `npc.interceptorIds` и quest index по `npcId` |

Slot-событие относится к месту и роли, NPC-событие — к самому персонажу.
[Квестовые привязки](quest-system-design.md#привязки-и-индексы) адресуют конкретных NPC и POI.
Один ID должен приходить в контекст из одного источника: runtime сохраняет список
как задан, а [валидатор](validation-contract.md) выявляет дубли.

## Вход и очередь

При входе в POI или новом подходе из POI к NPC создаётся снимок подходящих событий.
Возврат из внутреннего Frame в root продолжает существующее взаимодействие.
Для POI вход означает прибытие через мировой переход. Возврат из разговора
в POI root, в том числе после ухода NPC по расписанию, сохраняет посещение
и не запускает входные события POI заново.
Очередь разрешается до показа первого Frame: обычный root не мелькает перед сценой.

1. Собрать актуальные definitions, проверить conditions, appearance и лимиты.
2. Записать их в единственную `pendingEvents` текущего контекста.
3. Исполнять больший `priority` раньше; default — 100. Равные приоритеты имеют
   стабильный порядок по ID; содержимое не должно зависеть от случайного порядка.
4. Перед исполнением извлечь item из очереди и повторно проверить conditions.
   Если они уже не выполняются, пропустить событие без расходования лимита.
5. Учесть исполнение, выполнить check/result, применить effects и narrative.
6. Результат без перехода продолжает очередь. Открытый Frame приостанавливает
   её до возврата в root. После исчерпания очереди и подтверждения текущего текста
   доступны обычные варианты root.

Снимок делает цепочку конечной. Например, событие A изменило квестовую стадию
и добавило новое событие B: B дождётся следующего входа.
Если B уже было в снимке, но после A потеряло актуальность, повторная проверка
conditions отбросит его. Для обязательного продолжения сцены используй переходы
между Frames, а не расчёт на добавление нового Interceptor в текущую очередь.

Смена контекста очищает его очередь. Время, смена time slot и новый день
сохраняют оставшийся снимок входа: новые события не добавляются, исполненные
не возвращаются. Начатая входная сцена может продолжить свою очередь после
возврата в root с обычной повторной проверкой conditions ожидающих событий.
Например, фейсконтроль при входе не повторяется после ожидания внутри клуба.
Если NPC больше не занимает slot, разговор завершается и runtime возвращается
в POI-контекст без нового входного эпизода POI.

Системный [forceExit](tension-force-exit-and-poi-entry.md#force-exit) использует
эту же очередь. Его планирование и сохранение при refresh описаны там.

## Повторяемость

В корректном снимке ID встречается один раз и удаляется перед исполнением.
Только при новом входе событие может попасть в новую очередь.
Нужную повторяемость между входами автор задаёт состоянием и лимитами:

| Задача                              | Способ                                                           |
| ----------------------------------- | ---------------------------------------------------------------- |
| Повторять до получения доступа      | `conditions`, которые перестают выполняться после выдачи доступа |
| Не чаще раза в день                 | `executionLimit: { perDay: 1 }`                                  |
| Один раз за игру для субъекта       | `executionLimit: { total: 1 }`                                   |
| Не чаще раза в день, всего три раза | `executionLimit: { perDay: 1, total: 3 }`                        |

Начатый check расходует лимит при любом исходе. Если одноразовость естественно
следует из смены квестовой стадии или другого состояния, отдельный total необязателен.
Адрес счётчиков и дневного шанса определяется
[субъектом взаимодействия](interaction-runtime-state-design.md#память-исполнения).
Уход и повторный подход в тот же день не перебрасывают сохранённый `appearanceChance`.

## Примеры контента

Ниже — примеры definitions для условных NPC, POI и квестов. Их ID должны иметь
соответствующие определения и привязки в реестрах проекта.

### Первое знакомство

```ts
keeperIntro: {
  priority: 150,
  conditions: [{ type: 'timesMet', npcId: 'keeper', exact: 0 }],
  executionLimit: { total: 1 },
  result: {
    narrative: [{ speakerId: '$npc', text: 'Have not seen you around before.' }],
  },
}
```

Такой narrative объединится с текстом следующего события или root Frame в одну
показываемую порцию. `timesMet` ещё равен нулю до
[завершения встречи](npc-initial-data-design.md#встречи-и-отображаемое-имя), поэтому
`total: 1` явно фиксирует одноразовость вступления независимо от момента регистрации встречи.
Для знакомства достаточно этого условия и лимита; отдельный служебный квест
понадобится только при наличии собственной квестовой задачи.

### Фейсконтроль

```ts
'club:faceControl': {
  priority: 300,
  conditions: [{
    type: 'questVar',
    questId: 'clubAccess',
    key: 'hasPass',
    notEquals: true,
  }],
  result: {
    transition: { type: 'frame', frameId: 'club:faceControl' },
  },
}
```

Frame предлагает предъявить пропуск, подкупить охранника или уйти. Успешный
способ пройти контроль устанавливает `hasPass: true`, и событие теряет актуальность.
Если игрок ушёл без доступа, следующий подход снова запускает фейсконтроль.
Лимит `total: 1` здесь мешал бы задаче: после отказа проверка больше не работала бы.

### Случайная сцена в таверне

```ts
'tavern:randomFight': {
  priority: 50,
  appearanceChance: 0.1,
  executionLimit: { perDay: 1 },
  result: {
    transition: { type: 'frame', frameId: 'tavern:randomFight' },
  },
}
```

При успешном дневном броске сцена запускается на входе один раз в этот день;
в другой день она может появиться при новом входе. Шанс отвечает за появление, лимит — за число
запусков. Другие подходящие события из снимка также исполнятся по приоритету;
сам шанс не делает сцены взаимоисключающими.

### Фиксация нарушения без отдельной сцены

```ts
'sheriffOffice:recordTrespass': {
  conditions: [{
    type: 'questVar',
    questId: 'sheriffWarning',
    key: 'wasWarned',
    equals: true,
  }],
  result: {
    effects: [{
      type: 'setQuestVar',
      questId: 'sheriffWarning',
      key: 'enteredForbiddenOffice',
      value: true,
    }],
  },
}
```

Вход после предупреждения фиксирует нарушение. Такой silent Interceptor сразу
продолжает очередь; если она пуста, открывается root участка. Повторная установка
того же флага безопасна; одноразовое последствие потребовало бы условия или лимита.
Результат без перехода также может добавить narrative — отдельный Frame нужен
для сцены с собственными Actions, а не для любого текста.

### Обязательная квестовая конфронтация

По истечении срока квест переходит на `maraIsAngry`. Стадия
[привязывает](quest-system-design.md#привязки-и-индексы) Interceptor конфронтации
к NPC Мары. При следующем подходе он открывает Frame, в котором Actions позволяют
объясниться, отказаться или выбрать другой исход. Эти Actions переводят квест
на следующую стадию либо завершают его, снимая привязку конфронтации.

Так обязательность задаётся автоматическим началом сцены, а её исход остаётся
решением игрока. Для многошагового эпизода Interceptor открывает первый Frame,
последующие переходы выполняют обычные Actions.
