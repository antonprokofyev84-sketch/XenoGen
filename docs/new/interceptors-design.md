# Interceptors — зафиксированная модель

## Статус документа

Этот документ собирает решения по Interceptors в одном месте. Он заменяет прежнюю идею автоматических Actions.

Главное определение:

> **Action — выбор игрока. Interceptor — событие, которое система запускает независимо от выбора игрока при входе в конкретный контекст взаимодействия.**

Interceptor не является невидимой кнопкой и не смешивается с Actions в одном списке. Чаще всего он перехватывает вход и открывает Frame события, внутри которого игрок получает обычные Actions: ответить, уйти, заплатить, атаковать и так далее. Но Interceptor может быть и silent-событием без перехода во Frame: применить effects и сразу продолжить очередь.

## Как мы пришли к Interceptors

Обсуждение началось с квестового тайм-лимита.

Предполагалось, что после истечения срока квест может перейти на стадию `maraIsAngry`, которая добавляет Маре Action конфронтации. Возникла проблема: игрок может прийти к Маре и просто не нажать этот Action. Для обязательной сцены обычной кнопки недостаточно.

Первой идеей был **автоматический или принудительный Action**, который запускается сам при появлении в списке. Затем выяснилось, что тот же механизм может решать и другие задачи:

- первое представление NPC или POI;
- фейсконтроль при входе в клуб;
- засаду или другое событие при входе;
- обязательную квестовую сцену;
- появление случайного события в таверне;
- запуск или предложение квеста при выполнении условий и взаимодействии с нужным персонажем.

После этого проявилась концептуальная проблема: обычный Action обозначает действие, выбранное игроком. У автоматического события нет кнопки, `label`, disabled-состояния или осмысленного `cost`. Использовать одну сущность для двух разных ролей можно технически, но контракт становится неочевидным.

Поэтому сущности были разделены:

- **Action** запускается игроком;
- **Interceptor** запускается системой;
- обе сущности могут переиспользовать общие условия, проверки и форму результата;
- если после срабатывания нужен выбор игрока, Interceptor открывает Frame, а варианты поведения находятся в обычных Actions этого Frame.

Отдельно рассматривались служебные микроквесты для знакомства и других одноразовых событий. От этой идеи отказались: создавать квест только ради удаления вступительной сцены из доступных событий избыточно. Для знакомства достаточно Interceptor с условием по счётчику встреч.

## Ответственность сущностей

| Сущность | Ответственность |
|---|---|
| `Action` | Выбор, который игрок видит и может нажать |
| `Interceptor` | Автоматическое событие при входе в контекст |
| `Frame` | Сцена: текст, фон и доступные игроку Actions |
| `ActionResult` / `InterceptorResult` | Narrative, effects и допустимый для сущности переход |

Interceptor обычно открывает Frame. Например, фейсконтроль автоматически останавливает игрока, а Frame предлагает уйти, подкупить охранника или начать драку.

Если переход не указан, Interceptor применяет свой результат и движок сразу берёт следующий ID из текущей очереди. Это подходит для событий, которые должны только изменить состояние: например, вход в запрещённый участок может молча установить quest var о нарушении запрета.

`cost` принадлежит Actions внутри Frame. Interceptor не должен самовольно списывать ресурсы игрока.

## Предварительный контракт

Точная форма должна быть согласована с итоговыми типами Actions, но смысл полей зафиксирован:

```ts
interface ExecutionLimit {
  perDay?: number;
  total?: number;
}

type InterceptorTransition = {
  type: 'frame';
  frameId: FrameId;
};

interface InterceptorResult {
  narrative?: NarrativeBlock[];
  effects?: Effect[];
  transition?: InterceptorTransition;
}

type InterceptorCheck = ActionCheckRule & {
  onSuccess: InterceptorResult;
  onFail: InterceptorResult;
};

interface InitialInterceptorBase {
  /**
   * Определяет, участвует ли Interceptor в текущем входе.
   * Если хотя бы одно условие не выполнено, Interceptor
   * не включается в снимок входа.
   * Все условия объединяются через AND.
   */
  conditions?: ActionCondition[];

  /** Приоритет выполнения. Большее значение выполняется раньше. Default: 100. */
  priority?: number;

  /** Вероятность появления, использующая ту же память, что и Actions. */
  appearanceChance?: ActionNumber;

  /** Ограничение количества исполнений. */
  executionLimit?: ExecutionLimit;

}

type InitialInterceptor = InitialInterceptorBase & (
  | {
      result: InterceptorResult;
      check?: never;
    }
  | {
      check: InterceptorCheck;
      result?: never;
    }
);
```

Interceptor содержит либо `result`, либо `check`. `check` поддерживается обязательно как возможность системы: он позволяет автоматически запускать случайные события и квестовые сцены с разными результатами проверки. Если проверка конкретному событию не нужна, используется обычный `result`.

Квестовый Interceptor может непосредственно выполнить `setQuestStage` через обычный `result` либо `check.onSuccess/onFail`. Frame нужен только тогда, когда после автоматического срабатывания игрок должен увидеть сцену или сделать выбор.

Единственный переход Interceptor в первой версии — открытие Frame. Отсутствие `transition` означает применить narrative/effects и продолжить текущую очередь, а не остаться в каком-либо Frame.

У Interceptor нет:

- `label`;
- `requirements`;
- `cost`;
- disabled-состояния.

## `conditions` и `requirements`

Названия сохраняются, но получают явные комментарии.

```ts
interface BaseExecutable {
  /**
   * Определяет участие сущности во взаимодействии.
   *
   * Если хотя бы одно условие не выполнено:
   * - Action не показывается;
   * - Interceptor не включается в снимок входа.
   * Все условия объединяются через AND.
   */
  conditions?: ActionCondition[];
}

interface Action extends BaseExecutable {
  /**
   * Определяет возможность выполнить уже показанный Action.
   *
   * Если хотя бы одно требование не выполнено,
   * Action остаётся видимым, но отображается disabled.
   * Все требования объединяются через AND.
   *
   * Для Interceptor это поле не используется.
   */
  requirements?: ActionCondition[];
}
```

Коротко:

- `conditions` — существует ли сейчас Action или Interceptor в контексте;
- `requirements` — может ли игрок нажать уже видимый Action.

## Привязка к владельцам

Actions и Interceptors собираются отдельно.

Квестовая стадия может одновременно добавить владельцам оба вида сущностей:

```ts
interface InitialQuestStage {
  actionIdsByTarget?: Partial<
    Record<QuestTargetId, ActionId[]>
  >;

  interceptorIdsByTarget?: Partial<
    Record<QuestTargetId, InterceptorId[]>
  >;
}
```

Например, квест с пропуском в клуб может:

- добавить клубу Interceptor фейсконтроля;
- добавить Бобу Action «Спросить про пропуск».

```ts
{
  actionIdsByTarget: {
    bob: ['bob:clubPass:ask'],
  },

  interceptorIdsByTarget: {
    club: ['club:clubPass:faceControl'],
  },
}
```

Источники Interceptors собираются отдельно от Actions:

```text
POI-контекст
→ poi.interceptorIds
→ quest interceptorIdsByTarget[poiId]

slot/NPC-контекст
→ slot.interceptorIds
→ npc.interceptorIds текущего occupant
→ quest interceptorIdsByTarget[npcId]
```

Slot не является `QuestTargetId`. `slot.interceptorIds` содержит базовые события именно этого места и роли. Если такой Interceptor должен зависеть от квеста, его актуальность проверяется собственными квестовыми `conditions`; помещать `slotId` в `interceptorIdsByTarget` не нужно.

## Что считается входом

Снимок Interceptors создаётся при реальном переходе из родительского контекста в дочерний.

Для `slot/NPC` каждый новый подход считается отдельным входом:

```text
зал таверны → подойти к бармену
```

Если игрок закончил разговор, вернулся в зал и снова подошёл к бармену, создаётся новый снимок Interceptors бармена.

Возврат из внутреннего Frame в root того же NPC или POI новым входом не считается. Это продолжение уже начатого взаимодействия.

## Снимок и очередь

При входе runtime собирает массив Interceptors, актуальный для текущего контекста и time slot:

```ts
interface CurrentInteraction {
  // остальные данные взаимодействия
  pendingInterceptorIds: InterceptorId[];
}
```

Порядок работы:

1. Собрать Interceptors текущего NPC или POI из всех источников.
2. Проверить `conditions`, `appearanceChance` и лимиты.
3. Отсортировать Interceptors по `priority`.
4. Сохранить их ID в `pendingInterceptorIds`.
5. Извлечь следующий ID из массива, одновременно удалить его из очереди и непосредственно в этот момент повторно проверить его актуальность и `conditions`. Если Interceptor больше не актуален, молча отбросить ID и взять следующий.
6. Выполнить прошедший повторную проверку Interceptor.
7. Если результат открыл Frame, приостановить очередь. Если перехода нет, сразу перейти к следующему ID.

Если используется `pop()`, массив сортируется так, чтобы Interceptor с наибольшим `priority` находился последним.

При одинаковом `priority` можно использовать ID как дополнительный стабильный ключ. Смысл результата не должен зависеть от порядка Interceptors с одинаковым приоритетом.

Если `priority` не указан, используется `100`.

### Продолжение очереди

Если Interceptor открыл Frame, оставшаяся очередь приостанавливается. Silent Interceptor без перехода не создаёт паузу: после применения его результата очередь продолжается сразу.

- Если Action внутри Frame возвращает игрока в root того же контекста, runtime берёт следующий Interceptor из сохранённого массива.
- Если Action отправляет игрока в parent, другой POI, бой или иным способом завершает текущее взаимодействие, оставшаяся очередь удаляется.
- Если из Frame происходит переход глубже — в дочерний slot или дочерний POI, — очередь родительского контекста также удаляется. Дочерний контекст считается отдельным входом и собирает собственный снимок Interceptors. Возвращение из него не возобновляет старую очередь родителя.
- Когда очередь пуста, показывается обычный root Frame.

Пример:

```text
Вход в клуб
  → фейсконтроль
      → уйти: переход в parent, очередь удаляется
      → подкупить: возврат в root клуба, очередь продолжается
  → следующее событие из снимка
  → root клуба
```

### Пересборка при смене time slot

Смена time slot делает старый снимок неактуальным. После полного атомарного изменения времени runtime:

1. обновляет schedules и occupancy;
2. проверяет, существует ли ещё текущий interaction-контекст;
3. удаляет прежний `pendingInterceptorIds`;
4. собирает и сортирует новую очередь для актуального контекста и конечного time slot.

Если действие пересекло несколько time slots, промежуточные очереди не строятся: используется только конечное состояние времени.

Если после действия открыт root актуального контекста, новая очередь начинает исполняться сразу. Если игрок остаётся во внутреннем Frame, очередь сохраняется и ждёт возврата в root. Переход из Frame в parent, другой POI, дочерний контекст, бой или завершение interaction удаляет эту очередь по обычным правилам.

Результат `appearanceChance` остаётся дневным и при пересборке в тот же день не перебрасывается. Новая очередь отличается за счёт актуальных источников, `conditions`, execution limits, schedules и occupancy.

Если текущий NPC после обновления occupancy больше не занимает slot, его interaction-контекст завершается. Новая очередь для исчезнувшего NPC не строится; runtime возвращается к актуальному POI-контексту.

### Последствия снимка

- Один Interceptor присутствует в одной собранной очереди не более одного раза: его ID удаляется до исполнения. После смены time slot тот же ID может снова попасть в новую очередь, если его `conditions` и limits по-прежнему позволяют выполнение.
- Специальный `handledActionIds` не нужен.
- Повторная проверка `conditions` жёстко выполняется на шаге 5 — в момент извлечения конкретного ID из `pendingInterceptorIds`. Если предыдущий Frame изменил переменные и условия ожидающего Interceptor перестали выполняться, извлечённый ID молча сбрасывается, после чего runtime берёт следующий.
- Interceptors, появившиеся из-за изменения state уже после создания снимка, в текущую очередь не добавляются. Они смогут выполниться при следующем отдельном входе или пересборке после смены time slot.

Одинаковый ID не должен одновременно приходить из нескольких источников. Runtime не дедуплицирует список и не считает число источников: такое повторение является ошибкой initial-данных и проверяется development-валидатором.

Внутри одного time slot снимок делает цепочку конечной и не требует повторной полной сборки после каждого Frame.

## Повторяемость

Нужно поддержать три разных масштаба повторяемости.

### Один раз за одну очередь

Обеспечивается самой очередью: ID присутствует в снимке один раз и удаляется перед выполнением. Если событие не должно повториться после пересборки в новом time slot, его результат должен изменить содержательное состояние, от которого зависят `conditions`, либо использовать подходящий `executionLimit`.

### Ограничение за день

```ts
executionLimit: {
  perDay: 1,
}
```

Подходит для события, которое может происходить снова в другой день, но не должно повторяться после каждого нового подхода в тот же день.

### Общий лимит

```ts
executionLimit: {
  total: 1,
}
```

или:

```ts
executionLimit: {
  total: 3,
}
```

Подходит для ограниченного числа исполнений за игру. После достижения `total` Interceptor больше не попадает в новые снимки.

`perDay` и `total` могут использоваться одновременно:

```ts
executionLimit: {
  perDay: 1,
  total: 3,
}
```

Счётчики увеличиваются, когда Interceptor действительно начинает исполнение. Отброшенный из очереди ID с невыполненными `conditions` не учитывается; обе ветки начатого `check` учитываются как исполнение.

Если одноразовость уже естественно выражается состоянием квеста или мира, отдельный общий лимит не обязателен. Например, Interceptor квестовой конфронтации доступен только на конкретной стадии и исчезает после её смены.

## Runtime-память

Конкретная структура runtime-памяти будет определена вместе с новым interaction runtime. Текущий `interactionSlice` можно использовать только как пример отдельных приёмов: он создавался для прежней services-модели и будет почти полностью переписан.

Зафиксированы только требования:

- Actions и Interceptors хранятся и собираются отдельно;
- дневные execution-счётчики и сохранённые результаты `appearanceChance` очищаются полностью в конце дня, включая память активного interaction;
- счётчик `executionLimit.total` является долговременным и в конце дня не очищается;
- `pendingInterceptorIds` принадлежит текущему interaction-контексту, полностью заменяется при смене time slot и удаляется при завершении или переходе в другой контекст;
- точный выбор maps или массивов сейчас не является частью контракта.

Полные определения по-прежнему находятся в реестрах:

```ts
const ACTIONS: Record<ActionId, Action>;
const INTERCEPTORS: Record<InterceptorId, Interceptor>;
```

Это реестры initial-данных, а не runtime-память.

В текущих исходниках у сервисов уже существуют `executedTimes` и `maxExecutions`. Это только пример старой реализации. Новая форма `executionLimit: { perDay, total }` должна иметь одинаковую семантику для Actions и Interceptors независимо от будущего способа хранения.

## Счётчики встреч и посещений

Первое представление NPC использует счётчик встреч, а не отдельный boolean-флаг.

Счётчики обновляются при выходе из взаимодействия в не дочерний POI, но не более одного раза в календарный день.

Отдельная map для контроля дня не требуется:

- для NPC используется `lastDateMet`;
- для POI используется `lastTimeVisited`.

Общий принцип:

```ts
if (
  lastDateMet === null ||
  diffCalendarDays(lastDateMet, currentTime) > 0
) {
  timesMet += 1;
}

lastDateMet = currentTime;
```

Для `visitedTimes` применяется та же проверка через `lastTimeVisited`.

При первом входе Interceptors проверяются до увеличения счётчика. Поэтому условие `timesMet === 0` корректно обнаруживает первую встречу. Сам счётчик увеличится после завершения взаимодействия.

## Примеры

### Первое представление NPC

```ts
'bob:introduction': {
  priority: 100,

  conditions: [{
    type: 'timesMet',
    npcId: 'bob',
    exact: 0,
  }],

  executionLimit: {
    total: 1,
  },

  result: {
    transition: {
      type: 'frame',
      frameId: 'bob:introduction',
    },
  },
}
```

В конце Frame обычный Action возвращает игрока в root Боба. `total: 1` не позволяет знакомству повториться, если до первого выхода сменился time slot и очередь была пересобрана. Когда игрок покинет NPC-контекст, `timesMet` увеличится; в дальнейшем Interceptor также будет отсекаться содержательным условием.

Определение остаётся в initial-реестре, но не является постоянно активным runtime-объектом: после первой встречи оно отсеивается условием.

### Фейсконтроль

```ts
'club:faceControl': {
  priority: 300,

  conditions: [{
    type: 'questVar',
    questId: 'clubAccess',
    key: 'hasPass',
    notEquals: true,
  }],

  result: {
    transition: {
      type: 'frame',
      frameId: 'club:faceControl',
    },
  },
}
```

Frame предоставляет Actions:

- уйти в parent;
- предъявить или получить пропуск;
- подкупить охранника;
- начать драку.

Если игрок ушёл, при следующем входе фейсконтроль снова сработает. Успешный способ пройти контроль должен изменить состояние, проверяемое его `conditions`: в приведённом примере установить `hasPass: true`. Если доступ выдаётся временным предметом, definition фейсконтроля вместо quest var должен проверять отсутствие этого предмета. Тогда после возврата в root либо пересборки очереди в новом time slot фейсконтроль больше не будет актуален. Конкретная механика времени жизни временных предметов проектируется вместе с предметной системой.

### Повторяющееся случайное событие

```ts
'tavern:randomFight': {
  priority: 50,
  appearanceChance: 0.1,

  executionLimit: {
    perDay: 1,
  },

  result: {
    transition: {
      type: 'frame',
      frameId: 'tavern:randomFight',
    },
  },
}
```

Такое событие не является одноразовым сюжетным Interceptor. Оно может снова появиться в другой день.

На первом этапе не вводятся группы взаимоисключающих случайных событий и общий предел числа Interceptors за вход. Все Interceptors из снимка могут выполниться последовательно. Если длинные цепочки станут проблемой, к вопросу можно вернуться позже.

### Silent-событие

Игроку сказали не входить на участок шерифа. Сам вход может автоматически зафиксировать нарушение без отдельного диалога:

```ts
'sheriffOffice:recordTrespass': {
  priority: 100,

  conditions: [{
    type: 'questVar',
    questId: 'sheriffWarning',
    key: 'wasWarned',
    equals: true,
  }],

  result: {
    effects: [{
      type: 'setQuestVar',
      questId: 'sheriffWarning',
      key: 'enteredForbiddenOffice',
      value: true,
    }],
  },
}
```

После применения effect движок сразу берёт следующий ожидающий Interceptor. Если очередь пуста, открывается обычный root участка.

### Квестовая конфронтация

После истечения срока квест переводится на стадию, добавляющую Маре Interceptor:

```ts
maraIsAngry: {
  description: 'Мара узнала, что поручение не было выполнено.',

  interceptorIdsByTarget: {
    mara: ['mara:missingCourier:confrontation'],
  },
}
```

При следующем подходе к Маре Interceptor автоматически открывает Frame конфронтации. Игрок не может обойти сцену, просто проигнорировав кнопку в root.

Actions внутри Frame меняют стадию, завершают или проваливают квест и определяют дальнейший переход.

## Ограничение механизма

Interceptor работает только при входе во взаимодействие с конкретным NPC или POI. Он не является глобальным event bus.

Если квест должен стартовать независимо от того, посетил ли игрок владельца Interceptor, нужна отдельная глобальная точка проверки — например, обработка конца дня. Interceptor подходит для события вида «когда игрок в следующий раз придёт к Бобу», но не для события, которое обязано произойти в мире немедленно.

## Отброшенные варианты

### Automatic Action

Не используется. Action остаётся только выбором игрока, Interceptor является отдельной сущностью.

### `interactionStart` и `beforeRoot`

Отдельные фазы не используются.

Основной момент сборки — реальный вход в контекст. Возврат из Frame в root сам по себе не запускает новую фазу и продолжает сохранённую очередь. Исключение — смена time slot: она заранее заменяет старую очередь новым снимком, который начинает исполняться при следующем попадании в root.

### `handledActionIds`

Не используется. ID извлекается и удаляется до выполнения. После смены time slot повторяемость регулируют актуальные `conditions` и `executionLimit`, а не отдельный список обработанных IDs.

### Служебный микроквест для каждого знакомства

Не используется. Для первой встречи достаточно `timesMet === 0` вместе с `executionLimit.total: 1`, защищающим от пересборки очереди до первого выхода из NPC-контекста.

### Смешивание Actions и Interceptors в одном массиве

Не используется. У квестов и других источников для них отдельные свойства, а runtime собирает отдельные списки.

## Итог

Зафиксированная модель выглядит так:

- Action — выбор игрока;
- Interceptor — автоматическое событие при входе;
- Interceptor обычно открывает Frame, но может выполнить silent effects без перехода; решения игрока, если они нужны, описываются обычными Actions Frame;
- при каждом входе создаётся приоритетный снимок Interceptors; при смене time slot старая очередь удаляется и строится новая для конечного состояния мира;
- каждый подход к `slot/NPC` является отдельным входом;
- возврат в root того же контекста продолжает текущую очередь; очередь, пересобранная во внутреннем Frame после смены time slot, ждёт этого возврата;
- выход из контекста удаляет очередь;
- повторяемость регулируется условиями и `executionLimit.perDay/total`;
- `check` поддерживается;
- `cost`, `label` и `requirements` Interceptor не имеет;
- Actions и Interceptors используют отдельные привязки и отдельные массивы runtime-памяти;
- механизм может использоваться квестами, но не ограничен ими.
