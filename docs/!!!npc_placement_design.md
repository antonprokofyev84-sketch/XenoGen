# NPC Placement Design

## Базовая модель

У каждого POI есть базовое расписание активности.

У каждого NPC есть базовое расписание:

```ts
type NpcScheduleState =
  | 'work'
  | 'freeTime'
  | 'home'
  | 'hidden';
```

Работа имеет наивысший приоритет.

Если NPC назначен в рабочий слот POI, его базовое расписание резолвится через расписание рабочего места:

```text
если рабочий POI активен в этом таймслоте
→ состояние NPC становится work

иначе
→ сохраняется значение из базового расписания NPC
```

Резолвнутое расписание можно хранить в runtime-слайсе и пересчитывать только когда:

- NPC назначили или сняли с работы;
- изменилось расписание рабочего POI;
- изменилось базовое расписание NPC.

При обычной смене таймслота достаточно прочитать готовое значение.

## Структура NPC-слотов POI

Слоты группируются по типу активности, которому должно соответствовать текущее состояние NPC:

```ts
npcSlots: {
  work: [
    {
      id: 'bartender',
      role: 'bartender',
      npcIds: ['bob'],
      actions: ['trade', 'drink', 'rumors'],
    },
  ],

  freeTime: [
    {
      id: 'visitor_1',
      role: 'visitor',
      npcIds: ['bob', 'carl', 'mara'],
      actions: ['buyDrink'],
      chance: 70,
    },
    {
      id: 'visitor_2',
      role: 'visitor',
      npcIds: ['bob', 'carl', 'mara'],
      actions: ['buyDrink'],
      chance: 70,
    },
  ],

  home: [
    {
      id: 'resident',
      role: 'resident',
      npcIds: ['bob'],
    },
  ],
}
```

`hidden` не имеет собственных слотов. NPC с текущим состоянием `hidden` нигде не размещается.

## Семантика слота

Один объект слота всегда содержит максимум одного NPC.

Если в POI должно находиться несколько работников или посетителей, создаётся несколько отдельных слотов.

```text
id
— уникальный идентификатор конкретного слота внутри POI

role
— роль NPC в этом слоте
— может использоваться для изображения, одежды, анимации и специальных actions

npcIds
— список NPC-кандидатов для этого слота

actions
— дополнительные actions, доступные из-за роли NPC в слоте

chance
— шанс заполнения слота
— по умолчанию 100
```

Общие actions заведения хранятся на самом POI. В слоте остаются только действия, специфичные для конкретной роли.

---

## Размещение NPC

При заполнении POI система проходит по его слотам.

Для каждого слота:

1. Определяет тип секции: `work`, `freeTime` или `home`.
2. Берёт `slot.npcIds`.
3. Исключает NPC, уже размещённых в другом слоте этого таймслота.
4. Оставляет только NPC, у которых текущее резолвнутое состояние совпадает с типом секции.
5. Если кандидатов нет — слот остаётся пустым.
6. Выполняет проверку `slot.chance ?? 100`.
7. Если проверка провалена — слот остаётся пустым.
8. Иначе случайно выбирает одного NPC из оставшихся кандидатов.
9. Записывает выбранного NPC в occupancy.

```text
work slot     принимает NPC со state === work
freeTime slot принимает NPC со state === freeTime
home slot     принимает NPC со state === home
hidden        не размещается
```

После размещения NPC больше не может быть выбран другим слотом в этом таймслоте.

## Приоритеты

Приоритет задаётся не порядком обхода слотов, а резолвнутым расписанием NPC.

```text
активная работа перекрывает базовое расписание
иначе используется baseSchedule NPC
```

Пример:

```text
baseSchedule:
home, freeTime, freeTime, home

расписание таверны:
closed, closed, open, open

resolvedSchedule:
home, freeTime, work, work
```

NPC может участвовать только в слотах, соответствующих текущему значению `resolvedSchedule`.

## Дом как обычный POI

Дом остаётся обычным POI и использует секцию `home`.

```ts
npcSlots: {
  home: [
    {
      id: 'resident',
      role: 'resident',
      npcIds: ['bob'],
    },
  ],
}
```

Присутствие Bob дома определяется его резолвнутым расписанием:

```text
resolvedSchedule[currentSlot] === home
```

Доступность дома определяется отдельно:

```text
POI discovered
И
расписание дома разрешает посещение сейчас
И
хотя бы один NPC из home-слотов сейчас имеет state === home
```

Таким образом:

```text
Bob дома, но сейчас ночь и дом закрыт
→ дом виден, но недоступен

дом открыт, но Bob работает
→ дом виден, но недоступен

дом открыт и Bob дома
→ можно войти
```

Расписание дома отвечает не за физическое присутствие жильца, а за готовность принимать посетителей.

## Runtime-данные

Минимально нужны два производных runtime-состояния:

```ts
resolvedSchedulesByNpcId: Record<NpcId, ResolvedNpcSchedule>;

occupancy: {
  npcLocations: Record<NpcId, {
    poiId: PoiId;
    slotId: string;
  }>;

  poiOccupants: Record<PoiId, NpcId[]>;
};
```

`resolvedSchedulesByNpcId` хранит готовое расписание NPC после наложения работы.

`occupancy` хранит фактическое размещение NPC в текущем таймслоте.

Главное правило:

```text
resolved schedule определяет, в слот какого типа NPC может попасть

occupancy определяет, куда NPC фактически попал
```
